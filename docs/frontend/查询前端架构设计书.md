# 查询前端架构设计书

更新时间：2026-06-02

本文用于帮助开发者理解 Little Bear 普通用户查询前端的当前架构、模块边界、运行流程和后续开发约束。本文描述的是 `apps/web` 的实际实现，不是抽象愿景。

## 1. 架构目标

查询前端服务于企业普通用户的知识库问答场景。它的核心目标是让用户在登录后进行多轮问答、查看服务端历史会话，并能验证答案引用来源。知识库选择器用于限定检索范围；用户不选择知识库时，后端会自动搜索当前账号全部可查询知识库。

当前架构需要满足以下要求：

- 应用根组件只挂载查询工作区，不承载业务编排。
- 查询工作区 runtime 统一编排认证、知识库选择、会话、流式查询和来源预览。
- 会话、查询流、知识库、认证、来源预览各自拥有明确 composable。
- API 请求集中在 `src/api`，组件不直接拼接后端 URL 或调用 `fetch()`。
- 流式 SSE 事件必须经过运行时结构校验后再写入消息状态。
- 浏览器存储通过统一工具访问，避免散落 `sessionStorage` / `localStorage`。
- 前端只负责展示和交互提交，知识库权限、文档权限、查询可见性和字段裁剪由后端完成。

## 2. 顶层目录结构

当前查询前端入口位于 `apps/web/src`：

```text
apps/web/src
├── App.vue
├── main.ts
├── api/
├── components/
├── features/
├── styles/
└── utils/
```

主要职责如下：

| 目录 | 职责 |
| --- | --- |
| `api` | 后端 API 调用、DTO 类型、统一 HTTP 请求、SSE 解析和结构化错误 |
| `components` | 跨 feature 可复用的基础组件 |
| `features/auth` | 登录、token restore / refresh / logout 和当前用户状态 |
| `features/chat` | 查询工作区、会话列表、消息时间线、查询提交、SSE 状态更新 |
| `features/knowledge` | 当前用户可访问知识库列表、分页加载和选择状态 |
| `features/sources` | citation 来源详情、文档 chunk 预览和分页加载 |
| `styles` | 查询端全局样式、tokens、基础样式和聊天布局样式 |
| `utils` | 时间、展示格式化、浏览器存储等纯工具 |

## 3. 应用启动链路

查询前端启动链路如下：

```text
main.ts
-> App.vue
-> ChatWorkspace.vue
-> useChatWorkspaceRuntime()
-> auth / knowledge / conversations / query stream / source preview
```

关键文件：

- `apps/web/src/main.ts`
- `apps/web/src/App.vue`
- `apps/web/src/features/chat/ChatWorkspace.vue`
- `apps/web/src/features/chat/useChatWorkspaceRuntime.ts`

`App.vue` 当前只负责挂载 `ChatWorkspace.vue`，不应再新增认证、知识库、会话或查询业务逻辑。

`ChatWorkspace.vue` 负责页面结构：

- 左侧品牌区和新建对话按钮。
- 左侧会话列表。
- 左侧知识库范围选择器。
- 左下角当前用户与退出。
- 右侧查询状态栏。
- 未登录时显示登录面板。
- 已登录时显示消息列表、来源预览和输入框。

跨域编排全部由 `useChatWorkspaceRuntime.ts` 承担。

## 4. 工作区 Runtime

`useChatWorkspaceRuntime.ts` 是查询前端的工作区运行态入口。它不是通用全局 store，而是查询工作区这个 feature 的 public model。

它负责组装：

- `useAuthSession`
- `useKnowledgeBases`
- `useConversations`
- `useQueryStream`
- `useSourcePreview`

它负责的跨域流程：

- 页面挂载后恢复知识库选择和登录态。
- 登录成功后刷新知识库列表和服务端会话列表。
- 退出后清理知识库、会话和来源预览状态。
- 提交查询前重置来源预览。
- 查询完成后刷新会话列表。
- 选择历史会话时同步该会话实际使用的知识库范围。
- 删除当前会话后回到新对话状态。
- 打开 citation 时加载来源详情。

它不应负责：

- 直接解析 SSE frame。
- 直接构造 HTTP 请求。
- 直接操作 `sessionStorage` 或 `localStorage`。
- 直接实现消息排序、DTO 映射或 history 构造。

## 5. Feature 分层模型

当前查询端推荐的 feature 内部结构如下：

```text
features/<domain>
├── <DomainComponent>.vue
├── use<Domain>.ts
├── <domain>Mappers.ts
├── <domain>Timeline.ts
├── <domain>History.ts
└── types.ts
```

各层职责：

| 层级 | 职责 |
| --- | --- |
| `ChatWorkspace.vue` | 页面布局、组件组装、事件绑定 |
| `useChatWorkspaceRuntime.ts` | 查询工作区跨域编排 |
| `useAuthSession.ts` | 认证状态、token 生命周期和当前用户 |
| `useKnowledgeBases.ts` | 知识库列表、分页、选择和选择恢复 |
| `useConversations.ts` | 会话列表、服务端消息分页、删除和活动会话状态 |
| `useQueryStream.ts` | 查询提交、流式增量、回答消息更新和取消 |
| `useSourcePreview.ts` | 来源详情、文档 chunk 预览和分页加载 |
| mapper / timeline / history | DTO 映射、消息排序、history 构造等纯逻辑 |
| Vue 子组件 | 展示和 emit，不直接发请求 |

## 6. 当前 Feature 说明

### 6.1 认证域

入口：

- `apps/web/src/features/auth/LoginPanel.vue`
- `apps/web/src/features/auth/useAuthSession.ts`

主要职责：

- 登录。
- 恢复本地 session token。
- access token 过期前自动 refresh。
- 获取当前用户。
- 退出登录。

浏览器存储：

- key：`little-bear.web.auth`
- scope：`session`
- 访问方式：`utils/storage.ts`

认证域只负责用户登录态，不负责知识库权限判断。知识库权限由后端在知识库列表、查询和来源详情接口中完成。

### 6.2 知识库范围选择域

入口：

- `apps/web/src/features/knowledge/KnowledgeBaseSelector.vue`
- `apps/web/src/features/knowledge/useKnowledgeBases.ts`

主要职责：

- 加载当前用户可访问知识库。
- 支持分页加载更多。
- 支持全选、清空、单项切换；清空表示不限定知识库，由服务端自动搜索全部可查询知识库。
- 将选择过的知识库 ID 保存在 session storage。
- 刷新列表后与服务端可见知识库做 reconcile，避免保留无权限或已不可见的 ID；如果 reconcile 后为空，前端仍允许用户在后端自动范围内发起查询。

浏览器存储：

- key：`little-bear.web.kb-ids`
- scope：`session`
- 访问方式：`utils/storage.ts`

### 6.3 会话域

入口：

- `apps/web/src/features/chat/ConversationList.vue`
- `apps/web/src/features/chat/useConversations.ts`

主要职责：

- 服务端会话列表加载。
- 服务端单会话消息加载。
- 加载更早消息。
- 删除会话。
- 本地临时会话创建。
- 活动会话切换。
- 消息追加、消息更新和服务端 ID 替换。

已拆出的纯逻辑：

- `conversationIdentity.ts`：本地会话 ID、服务端会话 ID 判断。
- `conversationMappers.ts`：后端 conversation / message DTO 到前端 model 的映射。
- `conversationTimeline.ts`：消息时间线排序和会话状态推导。
- `conversationHistory.ts`：构造提交给后端的历史消息。

消息排序规则：

- 优先按 `createdAt` 升序。
- 同一时间戳下使用 `debugId` 聚组。
- 同一组内用户消息在助手消息前。
- 最后使用原始数组位置兜底，保证排序稳定。

### 6.4 查询流域

入口：

- `apps/web/src/features/chat/useQueryStream.ts`
- `apps/web/src/api/query.ts`

主要职责：

- 构造查询 payload。
- 发起非流式查询。
- 发起 SSE 流式查询。
- 处理 metadata、token、citation、done 和 error 事件。
- 将用户消息和助手占位消息写入会话。
- 流式 token 到达时增量更新助手消息。
- done 事件到达时写入最终答案、引用、置信度和降级状态。
- 支持 abort 取消。

`useQueryStream` 只依赖 `QueryConversationPort` 窄接口：

```text
ensureActiveConversation
buildHistoryMessages
createLocalMessage
appendMessages
updateMessage
replaceConversationId
isServerConversationId
```

这避免了查询流 composable 依赖 `useConversations` 的完整返回结构。

### 6.5 来源预览域

入口：

- `apps/web/src/features/sources/SourcePreviewPanel.vue`
- `apps/web/src/features/sources/useSourcePreview.ts`

主要职责：

- 点击 citation 后加载来源详情。
- 支持直接打开文档 chunk 列表。
- 支持 chunk 分页加载更多。
- 维护当前高亮 chunk。
- 显示来源内容状态。

来源详情和 chunk 列表仍必须依赖后端权限检查，前端不缓存或推断文档访问权限。

## 7. API 层设计

API 层位于 `apps/web/src/api`：

```text
api/http.ts
api/auth.ts
api/conversations.ts
api/documents.ts
api/health.ts
api/knowledge.ts
api/query.ts
api/types.ts
```

职责：

| 文件 | 职责 |
| --- | --- |
| `http.ts` | `requestJson`、`requestVoid`、`requestRaw`、base URL、Bearer header、结构化错误 |
| `auth.ts` | 登录、refresh、退出、当前用户 |
| `knowledge.ts` | 用户可访问知识库列表 |
| `conversations.ts` | 查询会话列表、详情、删除 |
| `documents.ts` | citation 来源详情和文档 chunk |
| `query.ts` | 非流式查询、SSE 流式查询、SSE 事件解析和 runtime guard |
| `types.ts` | API DTO 类型 |

API 层规则：

- 组件和 composable 不直接拼接 `/internal/v1/...`。
- 只有 `api/http.ts` 可以直接调用 `fetch()`。
- 业务代码必须直接引用具体 API 模块，例如 `@/api/auth`、`@/api/query`、`@/api/conversations`，不保留 `api/client.ts` 这类兼容聚合入口。
- `api/query.ts` 可以处理 SSE 读取和事件分发，但必须在写入业务状态前校验事件结构。
- DTO 字段名保持后端契约字段名，不在 API 层随意改名。
- 展示文案由 `utils/display.ts` 或 feature display 逻辑处理。

## 8. SSE 事件安全

查询流接口：

```text
POST /internal/v1/query-streams
```

当前支持的 SSE 事件：

```text
metadata
token
citation
done
error
```

前端在 `api/query.ts` 中对事件做 runtime guard：

- `isQueryStreamMetadata`
- `isQueryStreamDone`
- `isCitationData`
- `isQueryConfidence`
- `isNullableString`
- `isRecord`

设计原则：

- token 事件必须包含字符串 `delta`。
- citation 事件必须满足 `CitationData` 结构。
- done 事件必须满足完整 `QueryResponse` 结构。
- metadata 事件必须包含 debug、conversation、message、confidence、degraded 等元数据。
- error 事件必须符合后端结构化错误格式，否则按普通流式失败处理。

不允许把 unknown SSE payload 直接 cast 成业务 DTO 后写入消息状态。

## 9. 浏览器存储策略

统一工具：

- `apps/web/src/utils/storage.ts`

当前支持：

- `readStringFromStorage`
- `writeStringToStorage`
- `readJsonFromStorage`
- `writeJsonToStorage`
- `removeStorageItem`

支持 scope：

```text
local
session
```

当前查询端使用 session scope：

| Key | 内容 |
| --- | --- |
| `little-bear.web.auth` | access token、refresh token、过期时间 |
| `little-bear.web.kb-ids` | 已选择的知识库限定范围 ID；空数组表示服务端自动范围 |

约束：

- 不直接在业务代码中使用 `window.sessionStorage` 或 `window.localStorage`。
- 不持久化密码。
- 不持久化完整 prompt、文档原文或来源全文。
- token 仅保存在 session storage，浏览器会话结束后失效。

## 10. 状态所有权

当前状态所有权按以下规则分配：

```text
App.vue
  只挂载 ChatWorkspace

ChatWorkspace.vue
  页面布局、组件组装、事件绑定

useChatWorkspaceRuntime.ts
  查询工作区跨域编排

domain composable
  持有对应业务域的状态和动作

api
  请求、DTO、SSE 解析

utils
  无状态纯工具
```

典型查询数据流：

```text
用户输入问题
-> ChatComposer emit submit
-> ChatWorkspace 调用 submitQuery
-> useChatWorkspaceRuntime
-> useQueryStream
-> api/query.ts
-> 后端 query-streams
-> SSE metadata/token/citation/done
-> runtime guard
-> useQueryStream 更新会话消息
-> ChatMessageList 渲染答案和引用
```

典型登录数据流：

```text
LoginPanel submit
-> useChatWorkspaceRuntime.submitLogin
-> useAuthSession.login
-> api/auth.ts
-> 保存 session token
-> 获取 current user
-> 刷新知识库列表
-> 刷新服务端会话列表
```

## 11. 组件设计

当前主要组件：

- `LoginPanel.vue`
- `ConversationList.vue`
- `KnowledgeBaseSelector.vue`
- `ChatMessageList.vue`
- `ChatComposer.vue`
- `SourcePreviewPanel.vue`

组件规则：

- 组件通过 props 接收状态。
- 组件通过 emit 上报用户动作。
- 组件不调用 API。
- 组件不读取 storage。
- 组件不持有跨域状态。
- 组件内部只允许持有必要的局部交互状态。

- `apps/web/src/styles.css`

当前样式拆分：

```text
styles/tokens.css
styles/base.css
styles/chat.css
```

职责：

| 文件 | 职责 |
| --- | --- |
| `tokens.css` | 查询端基础 CSS 变量 |
| `base.css` | body、字体、box-sizing 等基础样式 |

部分组件仍保留 scoped style，例如消息列表、输入框、知识库选择器和来源预览。当前这可以接受，因为查询前端只有一个主工作区。若后续出现多个查询相关页面，应继续拆分 `chat.css`，避免单个样式文件继续增长。

## 13. 权限与安全边界

查询前端只负责：

- 是否显示登录面板。
- 是否显示当前用户可访问知识库列表。
- 是否允许用户提交查询。
- 是否展示后端返回的答案、引用和降级状态。

查询前端不负责：

- 判断某用户是否有权访问某知识库。
- 判断某文档是否有权查看。
- 判断某 chunk 是否可引用。
- 过滤无权限候选。
- 防止跨部门或跨企业越权。

这些必须由后端完成。

前端不得展示：

- 密码。
- refresh token / access token。
- secret value。
- 完整 prompt 内部结构。
- 不必要的内部 trace / request ID。
- 后端未授权的文档原文。

## 14. 当前架构约束

当前查询端已经完成核心架构收口，团队需要持续遵守以下约束：

- `useChatWorkspaceRuntime.ts` 是查询工作区聚合入口，后续新增能力应优先拆成子 composable，再由它组装。
- `useQueryStream.ts` 已经通过 `QueryConversationPort` 降低耦合，不要重新 import `useConversations` 的完整返回类型。
- `useConversations.ts` 已拆出 mapper、timeline、history 和 identity，不要再把纯逻辑塞回这个 composable。
- API 调用必须直接引用具体领域模块，不新增 re-export facade 或兼容 barrel。
- `utils/storage.ts` 是唯一浏览器存储入口，不要直接使用 `window.sessionStorage`。
- SSE 新事件必须先补 DTO 类型和 runtime guard，再交给业务 handler。

## 15. 新增查询端能力流程

新增查询前端能力时，按以下顺序执行：

1. 确认后端接口、权限和响应字段已经完成。
2. 在 `api/types.ts` 补 DTO。
3. 在对应 `api/<domain>.ts` 增加请求函数。
4. 如果是 SSE 新事件，在 `api/query.ts` 补事件 parser 和 runtime guard。
5. 在对应 feature composable 中新增状态和动作。
6. 如涉及跨域编排，再由 `useChatWorkspaceRuntime.ts` 组装。
7. Vue 组件只接收 props 并 emit 用户动作。
8. 如需存储，使用 `utils/storage.ts`。
9. 运行 `npm run typecheck:web` 和 `npm run build:web`。

## 16. 架构红线

以下行为会破坏当前查询端架构：

- 在 `App.vue` 中重新加入业务状态或业务动作。
- 在组件里直接调用 `fetch()`。
- 在组件里直接调用 `sessionStorage` 或 `localStorage`。
- 在 `useQueryStream.ts` 中重新依赖 `ReturnType<typeof useConversations>`。
- 把 SSE unknown payload 直接 cast 成业务 DTO。
- 在前端做权限过滤并认为后端可以不校验。
- 将完整 prompt、token、secret 或未授权文档内容展示给用户。
- 为了复用而把所有查询状态塞进一个全局 store。

## 17. 验收清单

查询前端改动完成后，至少执行：

```bash
npm run typecheck:web
npm run build:web
```

涉及主链路时，还应手动验证：

- 未登录时显示登录面板。
- 登录成功后知识库列表刷新。
- 没有可发现知识库时前端提示无可查询知识库，后端仍会在自动范围为空时返回结构化降级。
- 不选择知识库时可以发起查询，由后端自动搜索全部可查询知识库。
- 选择部分知识库后可以发起限定范围查询。
- 流式答案可以逐 token 显示。
- 非流式查询仍可用。
- 刷新页面后会话列表和消息顺序正常。
- 切换会话后用户问题显示在对应回答上方。
- 点击 citation 可以打开来源预览。
- 删除会话后列表和当前工作区状态正确。
- 退出登录后清理知识库、会话和来源预览状态。

## 18. 一句话总结

当前查询前端的核心架构是：

```text
App 只挂载查询工作区
ChatWorkspace 负责页面布局
useChatWorkspaceRuntime 负责跨域编排
domain composable 负责各自状态
api 层负责请求和 SSE 结构校验
utils 负责无状态工具
后端负责权限、分页、检索和字段裁剪
```

后续开发的判断标准很简单：如果代码只属于认证、知识库、会话、查询流或来源预览，就放回对应 feature；如果它跨域协调，就放在 `useChatWorkspaceRuntime.ts`；如果它是请求协议或 SSE 解析，就放在 `api`；如果它是无业务事实的纯工具，就放在 `utils`。

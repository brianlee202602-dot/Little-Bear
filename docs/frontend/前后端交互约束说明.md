# 前后端交互约束说明

更新时间：2026-06-03

本文说明 Little Bear 交付版前后端交互的职责边界，重点约束列表分页、筛选、字段收敛、详情权限检查、错误响应和 DTO 命名。

## 1. 总体原则

当前前端只负责：

- 展示后端返回的数据。
- 收集用户输入。
- 提交查询条件、分页参数和操作请求。
- 展示结构化错误。

当前后端负责：

- 分页。
- 筛选。
- 权限过滤。
- 业务状态判断。
- 字段裁剪。
- 详情接口二次权限检查。
- 错误码和 request_id 生成。

前端不能通过“先拉全量数据再本地筛选”替代后端查询，也不能通过隐藏菜单替代后端权限控制。

## 2. API client 组织

当前前端 API 调用集中在：

```text
apps/web/src/api
apps/admin/src/api
packages/frontend-sdk/src
```

约束：

- 组件不应散落拼接 `/internal` URL。
- 新增接口应先在对应 `src/api/<domain>.ts` 中封装。
- DTO 类型应放在对应 `*Types.ts` 或共享类型文件中。
- 流式查询可以使用 raw response，但仍应通过 API 模块封装。

当前 `http.ts` 负责：

- 拼接 `VITE_API_BASE_URL`。
- 设置 `Authorization: Bearer <token>`。
- JSON 请求设置 `content-type`。
- 将结构化错误包装为 `ApiRequestError`。

## 3. 认证传递

当前认证统一使用：

```text
Authorization: Bearer <jwt>
```

前端不得：

- 把 token 展示在页面上。
- 把 token 写入日志。
- 把 token 拼在 URL query 中。
- 用前端角色判断替代后端 scope 校验。

后端 route 每次都会从 header 提取 bearer token，并通过认证依赖校验 scope。

## 4. 列表接口分页

列表接口必须由后端分页，通用分页结构为：

```text
pagination.page
pagination.page_size
pagination.total
```

当前后端使用 `PaginationData` 表达该结构。典型 route 参数包括：

- `page`
- `page_size`

当前后端多数列表接口会限制 `page_size` 最大值，常见上限是 `100` 或 `200`。

前端必须：

- 把当前页和每页数量传给后端。
- 使用后端返回的 `total` 渲染分页器。
- 用户调整每页数量时重新请求后端。

前端不得：

- 一次请求大量数据再本地分页。
- 用前端分页替代后端权限过滤。
- 忽略后端返回的 `total`。

## 5. 列表接口筛选

业务筛选必须传给后端处理。当前常见筛选字段包括：

- `keyword`
- `status`
- `department_id`
- `kb_id`
- `user_id`
- `request_id`
- `trace_id`
- `error_code`
- `degraded`
- `degrade_reason`
- `resource_type`
- `risk_level`

不同接口只接受自身需要的筛选字段。

前端必须：

- 只提交接口支持的筛选参数。
- 空值不提交。
- 查询按钮触发后端请求。
- 切换筛选条件时重置或校正分页页码。

前端不得：

- 拉取全量列表后按 keyword / status 本地过滤。
- 自行构造部门、知识库或用户权限过滤。
- 在前端根据不可见字段推断权限。

## 6. 权限过滤

权限过滤只能在后端完成。

当前后端列表接口会在 service 层结合认证上下文、scope、企业、部门和知识库作用域过滤数据。例如：

- 普通用户知识库列表只返回当前用户可访问知识库。
- 管理后台知识库列表根据管理员 scope 和知识库管理权限返回。
- 用户、部门、角色、审计等接口要求对应管理 scope。
- 查询日志和模型调用日志按企业和审计权限读取。

前端菜单隐藏只是用户体验优化，不是权限边界。

## 7. 列表字段收敛

列表接口只应返回列表展示所需字段。

当前后端通过 schema 和 presenter 裁剪字段：

- 列表项返回摘要字段。
- 详情接口返回更多字段。
- 审计日志列表返回脱敏摘要。
- 模型调用日志列表返回调用摘要和 hash。
- 文档列表不返回完整文档原文。
- 查询日志列表不返回完整 prompt 或文档上下文。

列表接口不得返回：

- secret value。
- 完整 token。
- 密码。
- 完整 prompt。
- 文档全文。
- 完整 chunk 正文。
- 内部敏感 hash 之外的原始敏感内容。
- 前端不需要展示的权限策略细节。

如果页面需要详情，应调用详情接口，而不是让列表接口一次性返回所有内容。

## 8. 详情接口二次权限检查

详情接口必须重新做权限检查，不能因为列表可见就默认详情可见。

当前后端详情 route 仍会：

- 提取 bearer token。
- 校验 required scope。
- 进入 service。
- 按企业、用户、知识库、文档或日志 ID 做读取权限判断。

典型详情接口包括：

- 用户详情。
- 部门详情。
- 知识库详情。
- 文档详情。
- 文档版本、索引版本、chunk 预览。
- citation source。
- 查询日志详情。
- 模型调用日志详情。
- 审计日志详情。

前端不得缓存“列表可见”作为详情授权依据。

## 9. 错误响应结构

后端结构化错误包含：

- `request_id`
- `error_code`
- `message`
- `stage`
- `retryable`
- `details`

前端错误展示应优先使用：

- `message`
- `error_code`
- `request_id`
- `debug_id`

前端不得吞掉结构化错误，也不要只展示 HTTP status。管理后台和查询前端都应保留 request_id，方便开发人员和管理员查日志。

## 10. DTO 命名规则

当前 API 字段命名保持后端契约原名，主要是 snake_case，例如：

- `request_id`
- `page_size`
- `kb_id`
- `owner_department_id`
- `lifecycle_status`
- `index_status`
- `created_at`
- `updated_at`

前端 TypeScript DTO 应保持这些字段名，不在 API 层强行转换成 camelCase。

组件内部如果需要展示中文标签，可以在 UI 层做格式化，不改变 API DTO。

## 11. Lookup 与 option 接口

当页面只需要选择项时，应使用后端提供的 option / lookup 类接口，而不是拉取完整详情列表。

当前已有例子：

- 知识库 options。
- 文件夹 options。
- 部门 options。
- 用户可访问知识库列表。

这些接口也应支持分页、筛选和权限过滤。

## 12. 流式查询交互

查询前端支持 SSE 流式查询。约束：

- 请求仍由 `apps/web/src/api/query.ts` 封装。
- 认证仍使用 Bearer token。
- 前端只展示后端事件流中允许展示的内容。
- citation source、降级状态、置信度等由后端结果决定。
- 前端不得把模型返回的隐藏 source 占位符直接展示给用户。

## 13. 前端不得过量拉取后自行筛选

以下行为不允许：

- 为了搜索用户，先拉取所有用户再本地过滤。
- 为了搜索知识库，先拉取所有知识库再本地过滤。
- 为了展示文档版本，列表接口一次性返回所有 chunk 正文。
- 为了展示诊断日志，列表接口一次性返回完整 prompt 或文档上下文。
- 为了权限判断，前端拉取所有角色绑定再自行决定可见资源。

正确方式：

- 列表页传筛选条件给后端。
- 后端返回分页结果。
- 用户点击详情时再请求详情接口。
- 敏感详情仍由后端做权限检查和字段裁剪。

## 14. 新增接口检查清单

新增前后端交互接口时，应检查：

- 是否需要认证。
- required scope 是否明确。
- 是否需要后端分页。
- 筛选字段是否由后端处理。
- 列表字段是否只包含展示所需内容。
- 详情接口是否重新鉴权。
- 错误是否返回统一结构。
- DTO 是否同步更新。
- 前端 API client 是否集中封装。
- 是否需要同步 OpenAPI、权限矩阵和测试。

## 15. 交付边界

- 前端 API client 已模块化，但仍应持续避免组件直接拼 URL。
- 列表多数已后端分页和筛选，但新增接口仍需逐项检查。
- 前端显示中文标签，不代表后端枚举值需要翻译。
- 管理后台可以看到更多信息，但仍不能默认看到所有内部字段。

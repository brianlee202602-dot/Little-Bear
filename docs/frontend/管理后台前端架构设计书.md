# 管理后台前端架构设计书

更新时间：2026-06-02

本文用于帮助开发者理解 Little Bear 管理后台前端的当前架构、模块边界、运行流程和后续开发约束。本文描述的是 `apps/admin` 的实际实现，不是抽象愿景。

## 1. 架构目标

管理后台前端服务于企业内部知识库系统的配置、组织、用户、权限、知识库、导入索引和诊断运维管理。它的核心目标不是做一个“页面集合”，而是提供一个可维护、可扩展、权限边界清晰的后台应用。

当前架构需要满足以下要求：

- 应用根层只处理启动、认证、初始化状态、全局 provider 和页面挂载。
- 业务页面按 feature 拆分，每个 feature 拥有自己的运行态、数据加载、表单状态和弹窗状态。
- API 请求集中在 `src/api`，组件不直接拼接后端 URL。
- 列表、详情、分页、筛选和权限过滤以服务端返回为准，前端只负责展示和交互提交。
- 菜单隐藏只用于用户体验，不能被视为安全边界；所有管理接口仍必须由后端校验权限。
- 首屏不同步打入所有业务页面，后台业务 feature 通过动态 import 按需加载。
- 通用样式进入全局样式层，feature 私有样式由 feature 入口加载，禁止依赖某个页面静态导入带来的 CSS 副作用。

## 2. 顶层目录结构

当前管理后台前端入口位于 `apps/admin/src`：

```text
apps/admin/src
├── App.vue
├── main.ts
├── api/
├── app/
├── components/
├── composables/
├── features/
├── setup/
├── styles/
└── utils/
```

主要职责如下：

| 目录 | 职责 |
| --- | --- |
| `api` | 后端 API 调用、DTO 类型、统一 HTTP 请求和错误封装 |
| `app` | 应用生命周期、登录态、导航、provider、shell、feature outlet |
| `components` | 跨 feature 可复用的展示组件，如 modal、筛选条、分页、状态徽标 |
| `composables` | 跨 feature 的通用组合逻辑，目前主要是管理权限能力计算 |
| `features` | 业务域页面和业务域运行态，是管理后台的主体 |
| `styles` | 全局 tokens、基础布局、通用控件、弹窗、表格、响应式样式 |
| `utils` | 展示格式化、分页、错误、时间、集合、状态文案等纯工具 |

## 3. 应用启动链路

管理后台启动链路如下：

```text
main.ts
-> App.vue
-> AdminRoot.vue
-> useAdminAppRuntime()
-> provide session / capability / navigation / event bus
-> loading / login / dashboard / setup 四种顶层视图
```

关键文件：

- `apps/admin/src/main.ts`
- `apps/admin/src/App.vue`
- `apps/admin/src/app/AdminRoot.vue`
- `apps/admin/src/app/useAdminAppRuntime.ts`

`AdminRoot.vue` 当前只负责：

- 创建 `useAdminAppRuntime()`。
- 注册 `AdminSessionProvider`、`AdminCapabilityProvider`、`AdminNavigationProvider`、`AdminEventBus`。
- 根据 `activeView` 渲染 loading、登录页、后台 dashboard 或初始化页面。
- 将 `SetupPage` 作为异步组件加载，避免初始化页面进入已初始化后台的首包路径。

`AdminRoot.vue` 不应再持有部门、用户、知识库、配置、诊断等业务域状态。

## 4. App Provider 体系

管理后台使用 Vue provide / inject 提供跨 feature 的全局能力。当前 provider 位于 `apps/admin/src/app/providers`。

| Provider | 文件 | 职责 |
| --- | --- | --- |
| `AdminSessionProvider` | `adminSessionProvider.ts` | 当前用户、认证状态、token 获取、退出登录、用户展示名 |
| `AdminCapabilityProvider` | `adminCapabilityProvider.ts` | 根据当前用户 scopes 计算菜单和操作能力 |
| `AdminNavigationProvider` | `adminNavigationProvider.ts` | 当前 tab、可见 tab、tab 切换和路径同步 |
| `AdminEventBus` | `adminEventBus.ts` | 跨 feature 的轻量事件通知 |

Provider 的使用原则：

- feature 入口可以直接使用 provider。
- 普通页面组件优先通过 props 接收运行态，不直接注入 provider。
- provider 只暴露跨域基础能力，不放业务表单状态、不放业务弹窗状态、不放业务列表状态。
- 如果 feature 间需要同步刷新，优先使用 `AdminEventBus`，不要让 app root 重新成为业务协调器。

当前事件类型：

```ts
config.changed
department.changed
index.changed
knowledgeBase.changed
user.changed
```

## 5. 导航、权限与 Feature Registry

后台 tab 定义位于：

- `apps/admin/src/app/navigation.ts`
- `apps/admin/src/app/featureRegistry.ts`
- `apps/admin/src/app/AdminFeatureOutlet.vue`

当前 tab：

```text
config
departments
users
knowledge
diagnostics
```

`useAdminCapabilities.ts` 根据 `currentUser.scopes` 计算能力，例如：

- `canReadConfig`
- `canManageConfig`
- `canLoadDepartmentAdmin`
- `canLoadUserAdmin`
- `canLoadImportAdmin`
- `canLoadDiagnostics`
- `canLoadIndexOps`

`featureRegistry.ts` 负责把 tab 映射到 feature 入口组件：

```text
config      -> ConfigFeature
departments -> DepartmentsFeature
users       -> UsersFeature
knowledge   -> KnowledgeFeature
diagnostics -> DiagnosticsFeature
```

这些 feature 当前均通过 `defineAsyncComponent(() => import(...))` 动态加载。这样做的目的：

- dashboard 首包不再同步包含所有业务页面。
- 初始化页面不进入已初始化后台的首包路径。
- 后续新增大型 feature 时，可以自然按页面拆包。

必须明确：前端权限只控制菜单和按钮显示，不构成安全边界。所有后端接口仍要重新校验 token、scope、部门作用域、知识库权限和具体资源权限。

## 6. Feature 分层模型

当前推荐的 feature 内部结构如下：

```text
features/<domain>
├── <Domain>Feature.vue
├── <Domain>Page.vue / <Domain>Container.vue
├── <Domain>Modal.vue / 子组件
├── use<Domain>Runtime.ts
├── use<Domain>Actions.ts
├── use<Domain>State.ts
├── <domain>Display.ts
├── <domain>Types.ts
└── <domain>Feature.css
```

各层职责：

| 层级 | 职责 |
| --- | --- |
| `Feature.vue` | 获取 provider、创建 runtime、注册事件、加载初始数据、加载 feature 私有 CSS |
| `use<Domain>Runtime.ts` | 组装领域状态、动作、派生值，是 feature 的 public model |
| `use<Domain>State.ts` | 创建 reactive / ref 状态，不做远程请求 |
| `use<Domain>Actions.ts` | 封装远程写入、刷新、提交、删除等动作 |
| 页面 / 容器组件 | 接收 runtime 或 typed model，负责布局和事件转发 |
| 弹窗 / 子组件 | 只负责局部展示、表单输入和 emit，不直接处理全局副作用 |
| display / helper | 纯展示转换，如状态中文、tone、名称格式化、短 ID |

设计约束：

- 不允许把新业务 runtime 放回 `AdminRoot.vue` 或 `AdminDashboard.vue`。
- 不允许让 `app` 层直接 import 具体业务 action、业务 modal 或业务列表组件。
- 不允许让展示组件直接调用 `ensureAccessToken()` 后发请求；请求应在 runtime / action composable 中完成。
- 不允许使用 `[key: string]: any` 作为页面 model 的默认逃逸口。

## 8. API 层设计

API 层位于 `apps/admin/src/api`。当前设计为：

```text
api/http.ts          -> fetch、base URL、Authorization、结构化错误
api/<domain>.ts      -> 某个业务域的请求函数
api/<domain>Types.ts -> 某个业务域的 DTO 类型
api/client.ts        -> 兼容性的 re-export facade
```

当前主要 API 模块：

```text
setup
auth
config
audit
diagnostics
departments
users
roles
knowledgeBases
folders
documents
imports
indexOps
```

API 层规则：

- 所有请求必须经过 `requestJson()` 或 `requestVoid()`。
- Bearer token 由 runtime / action composable 调用 `session.ensureAccessToken()` 获取后传入。
- DTO 字段名保持后端契约字段名，不在 API 层做随意改名。
- 展示层需要中文文案时，在 `features/<domain>/*Display.ts` 或 `utils/display.ts` 处理。
- 新增接口时优先新建或扩展对应 domain API 模块，不要继续扩大 `client.ts` 的实际逻辑；`client.ts` 只作为 re-export facade。

## 9. 状态所有权

当前状态所有权按以下规则分配：

```text
app runtime
  只持有认证、初始化、导航、capability provider

feature runtime
  持有本 feature 的列表、详情、分页、筛选、busy、feedback、modal、form

component
  只持有临时 UI 状态，或通过 props / emit 与 runtime 交互

utils / display
  不持有状态，只做纯函数转换
```

典型数据流：

```text
用户点击按钮
-> 组件 emit
-> Feature runtime / action composable
-> session.ensureAccessToken()
-> api/<domain>.ts
-> 后端
-> runtime 更新状态
-> 页面组件重新渲染
```

跨 feature 数据同步：

```text
部门变更
-> DepartmentsFeature emit department.changed
-> 其他 feature 根据需要刷新 lookup
```

禁止模式：

- app root 集中保存所有 feature 状态。
- 页面组件直接调 API 并自行处理 token。
- 为了省事把多个业务域状态塞进一个全局 store。
- 弹窗组件直接刷新整页业务数据。
- 跨 feature 互相 import 对方的完整 runtime。

## 10. 样式架构

全局样式入口：

- `apps/admin/src/styles.css`

当前全局导入顺序：

```css
@import "./styles/tokens.css";
@import "./styles/base.css";
@import "./styles/layout.css";
@import "./styles/ui-controls.css";
@import "./styles/list-filter-layouts.css";
@import "./styles/operations.css";
@import "./styles/responsive.css";
```

全局样式职责：

| 文件 | 职责 |
| --- | --- |
| `tokens.css` | CSS 变量、基础色彩和间距 token |
| `base.css` | body、字体、基础 box-sizing |
| `layout.css` | 管理后台 shell、dashboard、panel 宽布局 |
| `ui-controls.css` | `.panel`、`.button`、`.field`、`.control`、`.summary`、`.tone` 等通用控件 |
| `list-filter-layouts.css` | 列表筛选区域通用布局 |
| `operations.css` | 后台通用表格、modal、操作区 facade |
| `responsive.css` | 全局响应式规则 |

Feature 私有样式：

- 配置：`features/config/configFeature.css`
- 诊断：`features/diagnostics/diagnosticsFeature.css`
- 知识库文档：`features/knowledge/knowledgeDocuments.css`
- 初始化：`styles/setup-controls.css` 由 `SetupPage.vue` 显式加载

重要约束：

- 通用类不能放在某个 feature 私有 CSS 中。
- feature 私有 CSS 不能承担全局按钮、输入框、panel 的基础样式。
- 动态 import 后，不能依赖“某个页面被静态导入所以 CSS 顺带全局生效”的隐式副作用。
- 新增样式时先判断是全局控件、布局规则、还是 feature 私有视觉，再放入对应文件。

## 11. 组件设计

跨 feature 组件位于 `apps/admin/src/components`：

- `BaseModal.vue`
- `ListFilter.vue`
- `PaginationBar.vue`
- `StatusBadge.vue`

组件设计原则：

- 通用组件只接受明确 props，并通过 emit 抛出用户动作。
- 通用组件不读取业务 provider。
- 通用组件不调用 API。
- 通用组件不包含某个业务域的文案、权限判断或 DTO 结构。

Feature 内组件可以包含业务文案和业务布局，但仍应避免直接请求 API。

## 12. 权限与安全边界

管理后台前端使用 scopes 做三件事：

- 控制菜单是否可见。
- 控制按钮是否可点。
- 控制是否加载某些 feature 数据。

前端不负责最终授权。最终授权必须在后端完成。

前端必须避免展示以下内容：

- secret value
- 完整 token
- 密码
- 完整 prompt
- 文档原文
- 过长内部 hash
- 不必要的 trace / request 内部 ID

列表页只展示列表字段；详情内容应通过详情接口或详情弹窗按需加载。

## 13. 构建与性能策略

当前管理后台使用 Vite + Vue 3 + TypeScript。

性能策略：

- `featureRegistry.ts` 对业务 feature 使用动态 import。
- `AdminRoot.vue` 对 `SetupPage` 使用动态 import。
- API client 拆分为 domain module，避免巨型 client 文件继续增长。
- CSS 分为全局基础样式和 feature 私有样式，避免所有业务样式无条件进入首屏。

当前构建门禁：

```bash
npm run typecheck:admin
npm run build:admin
```

如果新增大型 feature，必须检查 build 输出，避免重新出现首包体积过大。

## 14. 新增管理页面流程

新增一个管理后台页面时，按以下顺序执行：

1. 在后端补齐接口、权限 scope、分页、筛选和错误结构。
2. 在 `apps/admin/src/api` 新增 `<domain>.ts` 和 `<domain>Types.ts`。
3. 在 `features/<domain>` 新增 `<Domain>Feature.vue`。
4. 在 feature 入口中使用 `useAdminSessionProvider()`、`useAdminCapabilityProvider()` 和必要的 `useAdminEventBus()`。
5. 新增 `use<Domain>Runtime.ts`，持有本 feature 的列表、筛选、分页、busy、feedback、modal 和 form 状态。
6. 把远程动作拆入 `use<Domain>Actions.ts` 或更细子模块。
7. 页面组件只接收 runtime / model 并 emit 用户动作。
8. 如需菜单入口，更新 `navigation.ts` 和 `featureRegistry.ts`。
9. 如需展示权限，更新 `useAdminCapabilities.ts`。
10. 如需样式，按全局控件 / 全局布局 / feature 私有样式分类放置。
11. 运行 `npm run typecheck:admin` 和 `npm run build:admin`。

## 15. 当前过渡点与后续约束

当前架构已经从“巨型根组件协调全部业务”迁移到“app provider + feature 自治”。但仍有几个需要团队注意的过渡点：

- `UsersFeature.vue` 和 `KnowledgeFeature.vue` 仍会组装较大的 typed model，用于向历史容器组件传递大量展示和动作能力。这个模式可接受，但不应继续扩大。
- 知识库域是最大业务域，新增能力必须优先进入子 runtime / 子 action / 子 modal，而不是追加到 `useKnowledgeAdminRuntime.ts`。
- `api/client.ts` 仍作为 re-export facade 存在，不能重新把请求逻辑写回这个文件。
- `setup-controls.css` 仍作为 setup 样式 facade 存在，但通用 UI 样式已经进入 `ui-controls.css`，不得再让其他页面依赖 setup CSS。
- 当前没有引入 Pinia。若未来引入 store，只能用于明确跨页面共享且生命周期稳定的状态，不应用来替代 feature runtime。

## 16. 架构红线

以下行为会破坏当前架构：

- 在 `AdminRoot.vue` 中新增业务域状态。
- 在 `AdminDashboard.vue` 中直接 import 具体业务页面。
- 在 `featureRegistry.ts` 外绕过 registry 挂载业务页面。
- 在页面组件中直接调用 `fetch()` 或拼接 `/internal/v1/...`。
- 在组件中直接展示后端未裁剪的完整详情、hash、prompt、文档原文或 secret。
- 在前端做权限过滤并认为后端可以不校验。
- 将通用按钮、输入框、panel 样式放入某个 feature CSS。
- 新增 `any` 作为页面 model 或 action options 的逃逸口。
- 为了共享数据而让两个 feature 互相 import 对方完整 runtime。

## 17. 验收清单

管理后台前端改动完成后，至少执行：

```bash
npm run typecheck:admin
npm run build:admin
```

涉及主链路或页面结构变更时，还应手动检查：

- 登录页是否正常。
- 普通员工是否无法进入管理后台。
- 不同权限用户菜单是否正确隐藏。
- 列表筛选按钮是否对齐。
- 分页是否由后端 total 驱动。
- 弹窗是否不会溢出视口。
- feature 动态加载后样式是否仍正常。
- 浏览器 console 是否无明显错误。

涉及 API DTO、权限或字段裁剪时，还应同步检查：

- `docs/contracts/openapi.yaml`
- 后端 `api/schemas`
- 前端 `api/<domain>Types.ts`
- 管理后台页面展示字段
- 后端权限矩阵和审计事件

## 18. 一句话总结

当前管理后台前端的核心架构是：

```text
App Root 负责生命周期和全局 provider
Dashboard 负责 shell 和 feature outlet
Feature 负责自己的状态、动作、页面和样式
API 层负责请求和 DTO
Utils / Components 负责无业务归属的复用能力
后端负责真正权限、分页、筛选和字段裁剪
```

后续开发的判断标准很简单：如果某段代码只属于一个业务域，就放回该 feature；如果它跨业务域复用但不含业务事实，就放入 components / utils / styles；如果它是认证、能力、导航或事件，就放在 app provider。不要再把管理后台退回一个巨型协调器。

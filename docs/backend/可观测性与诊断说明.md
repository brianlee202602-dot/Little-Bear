# 可观测性与诊断说明

更新时间：2026-06-03

本文说明 Little Bear 当前后端可观测性能力，包括请求链路标识、查询日志、模型调用日志、审计日志、检索诊断和索引健康检查。

## 1. 设计目标

当前可观测性设计服务于三个目标：

- 让开发人员能定位一次查询为什么得到这个答案或为什么降级。
- 让管理员能在后台查看模型调用、检索质量、索引状态和高风险操作。
- 在不泄露 secret、token、完整 prompt 和文档原文的前提下保留排障线索。

## 2. request_id 与 trace_id

`RequestContextMiddleware` 会为每个请求设置：

- `request_id`：优先读取请求头 `x-request-id`，否则生成 `req_<uuid>`。
- `trace_id`：优先读取请求头 `x-trace-id`，否则生成 `trace_<uuid>`。

响应头会返回：

- `x-request-id`
- `x-trace-id`

这两个 ID 会进入查询日志、模型调用日志、审计日志和部分错误响应。排障时应优先使用这两个 ID 串联一次请求的多个记录。

## 3. query logs

query logs 记录一次查询请求的业务摘要。

当前记录内容包括：

- request_id / trace_id。
- 用户、企业、知识库范围。
- query hash，而不是完整 query 原文。
- 是否降级和降级原因。
- active config version、权限版本、索引版本摘要。
- 延迟、候选数量、引用数量。
- query scope mode、解析后的知识库数量、rewrite 数量。
- 结构化错误码和摘要。

query logs 用于回答：

- 用户这次查了哪个范围。
- 查询是否降级。
- 降级原因是什么。
- 检索候选和引用数量是否异常。
- 本次查询使用了哪个配置版本和索引版本。

## 4. query retrieval diagnostics

query retrieval diagnostics 记录检索阶段诊断信息，用于解释“为什么召回了这些 chunk”或“为什么没有召回”。

当前诊断重点包括：

- query rewrite 结果。
- 多 query 召回信息。
- 关键词召回。
- 向量召回。
- 融合和 rerank。
- candidate gate。
- 上下文构建。
- 引用数量和候选数量。

该诊断信息跟 query log 关联，不作为普通用户展示内容。管理后台查询日志详情中可以查看相关诊断摘要。

## 5. model call logs

model call logs 记录模型 provider 调用摘要。当前不会记录完整 prompt、文档原文或 secret。

当前记录内容包括：

- request_id / trace_id。
- caller，例如查询回答、rerank、embedding 等调用方。
- 模型名称和模型类型。
- provider 路由。
- 调用状态、耗时、错误码。
- token 使用摘要。
- prompt hash、input hash、output hash。
- 是否降级。
- config version。

model call logs 用于回答：

- LLM、rerank 或 embedding 是否被调用。
- provider 是否返回 HTTP 错误。
- 401 是否来自模型认证配置。
- 调用耗时是否异常。
- 降级是否由模型链路触发。

## 6. audit logs

audit logs 记录高风险操作和关键状态变化。当前审计日志用于管理和安全排查，不用于替代业务事实源。

典型审计场景包括：

- 配置发布、发布失败、归档等配置生命周期操作。
- 查询中发生 citation 自动修复或高风险降级。
- 权限、文档、索引等关键操作。

audit logs 关注：

- actor。
- action。
- resource。
- result。
- risk level。
- request_id / trace_id。
- 配置、权限、索引相关 hash 或摘要。

审计日志不应包含 secret value、完整 token、完整 prompt 或未脱敏文档原文。

## 7. index health

index health 由索引运维能力读取 PostgreSQL 索引账本，并可选探测 Qdrant collection 状态。

当前检查内容包括：

- Qdrant collection 是否存在。
- Qdrant points 数量是否可读取。
- 向量维度是否与账本期望一致。
- Qdrant points 是否少于 active refs。
- active index ref 数量是否异常。
- pending delete 是否需要清理。
- failed index versions 是否存在。

常见问题码包括：

- `qdrant_inspector_unavailable`
- `qdrant_unreachable`
- `qdrant_collection_missing`
- `qdrant_count_unavailable`
- `qdrant_vector_size_mismatch`
- `qdrant_points_less_than_active_refs`
- `active_index_ref_count_mismatch`
- `pending_delete_cleanup_required`
- `failed_index_versions_present`

index health 用于回答：

- Qdrant 中的索引是否与 PostgreSQL 账本一致。
- 文档重建索引后 active refs 是否正常。
- 是否存在待删除或失败索引版本。

## 8. 管理后台诊断页面

当前管理后台诊断能力包括：

- 查询日志列表与详情。
- 查询检索诊断详情。
- 模型调用日志列表与详情。
- 审计日志。
- 索引运维和 collection health。
- Qdrant 快照入口。

这些页面的职责是帮助管理员和开发人员定位问题，而不是展示内部原文或敏感信息。

## 9. 常见排障路径

### 9.1 登录返回 `SERVICE_BOOTSTRAP_UNAVAILABLE`

排查顺序：

1. 查看 setup state 是否 initialized。
2. 查看 active config 是否存在。
3. 查看 ServiceBootstrap 最近检查是否通过。
4. 检查 Redis、MinIO、Qdrant、模型 provider 和 Secret Store。
5. 检查数据库 migration revision 是否达到当前要求。

### 9.2 查询返回 LLM HTTP 错误

排查顺序：

1. 使用 request_id 或 trace_id 查询 model call logs。
2. 查看 caller 是否为 query answer。
3. 查看 error_code 和 provider route。
4. 如果是 401，检查 model gateway 或 provider auth token ref。
5. 检查 Secret Store 是否存在对应 secret。

### 9.3 查询无答案或降级

排查顺序：

1. 查看 query log 的 degrade_reason。
2. 查看 retrieval diagnostics，确认 rewrite、召回、融合、rerank 和 quality gate。
3. 查看引用数量和候选数量。
4. 检查用户可访问知识库范围。
5. 检查文档生命周期、索引状态和 access block。

### 9.4 索引健康不可读

排查顺序：

1. 查看错误码是否为 `INDEX_HEALTH_UNAVAILABLE`。
2. 检查 PostgreSQL 索引账本查询是否失败。
3. 检查 active config 中 Qdrant 配置。
4. 检查 Qdrant 服务可达性和 collection 名称。
5. 检查是否存在 pending delete 或 failed index versions。

## 10. 当前边界

- 当前模型调用日志只保存摘要和 hash，不提供 prompt 原文回放。
- 当前检索诊断用于排障，不作为用户可见解释链。
- 当前 Redis 未作为统一日志或链路追踪系统使用。
- 当前没有接入 OpenTelemetry 分布式追踪。

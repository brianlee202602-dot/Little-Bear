# 数据库迁移与版本管理说明

更新时间：2026-06-03

本文说明 Little Bear 交付版数据库迁移入口、新增 migration 的规则，以及 migration 与 ServiceBootstrap 的关系。

## 1. 迁移入口

仓库使用 Alembic 管理 PostgreSQL schema。迁移入口位于：

```text
apps/api/migrations
```

交付版 Schema migration 文件为：

```text
apps/api/migrations/versions/0013_little_bear_release_schema.py
```

该文件的 revision 为 `0013_query_log_scope_summary`，`down_revision = None`，用于让空库一步创建交付版系统需要的完整结构。

## 2. 空库初始化流程

空库部署时，执行顺序应为：

```bash
make PYTHON=.venv/bin/python db-upgrade
make PYTHON=.venv/bin/python db-current
```

迁移完成后再启动 API，并通过 setup 流程初始化系统、写入 active config 和 Secret。

不能跳过 migration 直接启动业务 API。setup guard 会在数据库不可用、migration 不满足要求或系统未初始化时拒绝普通业务接口。

## 3. 交付版迁移覆盖范围

交付版迁移创建的主要结构包括：

- 企业、部门、用户、角色、角色绑定。
- 配置版本、active config 状态、Secret Store。
- 知识库、知识库访问对象、文件夹、文档、文档版本。
- chunk、索引版本、chunk index ref、关键词索引账本。
- import job。
- audit log。
- query log、query retrieval diagnostics。
- model call log。
- query conversation。
- access block 和权限相关账本。

这些结构是 PostgreSQL 事实源。MinIO、Qdrant、Redis 和模型 provider 都不替代 PostgreSQL 中的业务事实。

## 4. 新增结构如何追加 migration

新增表、字段、索引、约束或枚举值时，应追加新的 Alembic migration，而不是修改已经发布的 migration 语义。

推荐步骤：

1. 明确业务事实源是否确实需要 PostgreSQL schema 变更。
2. 新增一个 revision，`down_revision` 指向当前 head。
3. 在 migration 中表达表结构、外键、唯一约束、CHECK 约束、索引和默认值。
4. 必要时写入数据回填逻辑。
5. 更新后端 ORM / repository / schema / presenter。
6. 更新接口契约、数据库契约和相关文档。
7. 增加或更新测试。
8. 执行 `db-upgrade`、`db-current` 和后端测试。

约束不能只写在 service 代码里。只要是业务必须成立的不变量，应尽量在数据库层表达。

## 5. 已发布 migration 维护规则

已经被环境执行过的 migration 不会因为文件内容改变而自动重新执行。如果直接修改已发布基线，会导致：

- 新空库和已迁移数据库 schema 不一致。
- Alembic 版本号相同但实际结构不同。
- ServiceBootstrap 只能看到 revision 已满足，无法知道结构漂移。
- 测试环境和真实环境出现难以定位的差异。

因此，发布后的结构变更必须追加新 migration。交付环境不得通过手工修改 Alembic 版本表规避 migration。

## 6. migration 与 ServiceBootstrap 的关系

ServiceBootstrap 会校验数据库 schema revision 是否达到当前期望值。当前期望 revision 来自 migration 文件中的 revision 定义。

业务 API 开放前需要同时满足：

- PostgreSQL 可连接。
- migration revision 满足交付版代码要求。
- system state 中记录的 schema migration version 与当前要求一致。
- 系统已初始化。
- active config 存在。
- ServiceBootstrap 关键依赖检查通过。

如果 migration 不满足要求，setup guard 会返回 `SETUP_MIGRATION_REQUIRED`，普通业务接口不可用。

## 7. 与 ServiceBootstrap 相关的 migration 注意点

新增 migration 时，如果该结构会影响 bootstrap、配置发布、Secret、外部依赖探测或系统状态，应同步检查：

- `system_state` 是否需要记录新的 schema migration version。
- ServiceBootstrap 是否需要新增检查项。
- 配置发布依赖校验是否需要新增 required dependency。
- setup 初始化是否需要写入新表默认数据。
- 相关管理后台页面是否需要更新。

## 8. 迁移验收清单

新增 migration 后至少检查：

- 空库执行 `db-upgrade` 成功。
- `db-current` 显示当前 head。
- 后端单元测试通过。
- 关键业务链路可以完成 setup 和 ServiceBootstrap。
- 新字段、索引和约束在数据库中真实存在。
- 删除、权限、索引和查询相关状态没有绕过 fail closed 边界。

## 9. 交付边界

- migration 只负责 schema 和必要回填，不负责启动外部服务或写入 secret 明文。
- 交付版数据库以 `0013_query_log_scope_summary` 为 schema head；新增结构变更通过追加 migration 演进。

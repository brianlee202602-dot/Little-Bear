# 缓存设计说明

更新时间：2026-06-03

本文说明 Little Bear 当前缓存相关实现状态，以及后续接入 Redis 业务缓存时必须遵守的边界。本文按当前代码事实编写：当前 Redis 已作为基础设施和 ServiceBootstrap 依赖接入，但业务缓存读写尚未实现。

## 1. 当前结论

当前系统没有真正启用业务缓存。

已经存在的缓存相关能力：

- `docker-compose.yml` 提供 Redis 服务。
- active config schema 包含 `redis` 和 `cache` 配置段。
- ServiceBootstrap 会对 Redis 执行最小 PING 检查。
- 数据库基线中存在 `query_cache_entries` 表。
- setup payload validator 明确禁止跨用户最终答案缓存。
- `ConfigService` 有进程内 active config TTL 缓存。
- auth runtime 有按 active config version 缓存的 JWT 运行时配置。

尚未实现的能力：

- 没有 Redis client 封装。
- 查询链路没有读取 Redis 缓存。
- 查询链路没有写入 Redis 缓存。
- `query_cache_entries` 目前没有接入 service 读写。
- 权限上下文缓存未实现。
- 查询 embedding 缓存未实现。
- 检索结果缓存未实现。
- 最终答案缓存未实现。
- Redis 不可用时降级为无业务缓存运行尚未实现。

因此，当前不能把 Redis 描述为已经承载查询缓存、权限缓存、限流、锁或配置通知。

## 2. 当前 Redis 使用范围

当前 Redis 只在以下位置体现：

- `docker-compose.yml`：启动本地 Redis，开启 AOF。
- active config：保存 Redis URL、连接池和 cache strategy 配置。
- ServiceBootstrap：通过 RESP PING 检查 Redis 是否可达。

ServiceBootstrap 当前把 Redis 作为关键依赖。Redis 不可达时，ready 检查不会通过，业务 API 可能返回 `SERVICE_BOOTSTRAP_UNAVAILABLE`。

## 3. 当前配置结构

active config schema 中 Redis 配置包含：

- `redis.url`
- `redis.pool.max_connections`
- `redis.pool.connect_timeout_ms`
- `redis.pool.socket_timeout_ms`
- `redis.pool.retry_on_timeout`
- `redis.cache_strategy.permission_context_enabled`
- `redis.cache_strategy.query_cache_enabled`
- `redis.cache_strategy.rate_limit_enabled`
- `redis.cache_strategy.lock_enabled`
- `redis.cache_strategy.config_notify_enabled`

cache 配置包含：

- `permission_context_ttl_seconds`
- `query_embedding_enabled`
- `query_embedding_ttl_seconds`
- `retrieval_result_enabled`
- `retrieval_result_ttl_seconds`
- `final_answer_enabled`
- `final_answer_ttl_seconds`
- `cross_user_final_answer_allowed`

当前 schema 对最终答案缓存有硬约束：

- `final_answer_enabled` 必须为 `false`。
- `final_answer_ttl_seconds` 必须为 `0`。
- `cross_user_final_answer_allowed` 不允许为 `true`。

这意味着当前版本不允许启用最终答案缓存，更不允许跨用户复用最终答案。

## 4. 当前数据库缓存账本

当前 migration 中存在 `query_cache_entries` 表。该表是查询缓存账本的预留结构，字段包括：

- `cache_key`
- `enterprise_id`
- `user_id`
- `entry_type`
- `permission_filter_hash`
- `request_filter_hash`
- `kb_ids_hash`
- `query_hash`
- `config_version`
- `permission_version`
- `index_version_hash`
- `model_route_hash`
- `prompt_template_version`
- `value_json`
- `created_at`
- `expires_at`

`entry_type` 当前允许：

- `query_embedding`
- `retrieval_result`
- `final_answer`

表约束要求 `final_answer` 类型必须带 `user_id`。虽然表结构保留了最终答案缓存类型，但当前配置 schema 禁止启用最终答案缓存。

## 5. 允许考虑的缓存对象

基于当前 schema 和账本结构，后续真正接入业务缓存时，只应从以下对象开始：

### 5.1 权限上下文缓存

目标：

- 缓存 Permission Service 构建出的权限过滤条件或权限摘要。

必要限制：

- 必须包含企业、用户、角色绑定、部门作用域、知识库作用域和权限版本。
- 权限收紧、角色变更、部门变更、知识库访问对象变更后必须失效。
- 缓存命中后仍要执行必要的 access block 检查。

当前状态：

- 未实现。

### 5.2 query embedding 缓存

目标：

- 对同一规范化 query、同一 embedding 模型路由和同一配置版本复用 query embedding。

必要限制：

- key 必须包含 query hash、config version、model route hash、embedding 模型维度或模型版本。
- embedding provider 切换后不得复用旧 embedding。

当前状态：

- 数据表支持 `query_embedding` 类型。
- 查询链路未实现读写。

### 5.3 retrieval result 缓存

目标：

- 缓存同一查询范围下的召回、融合或 rerank 后候选摘要。

必要限制：

- key 必须包含权限过滤 hash、请求过滤 hash、kb_ids hash、query hash、config version、permission version、index version hash 和 model route hash。
- 缓存命中后仍要做 access block 和引用有效性轻量校验。
- 权限收紧或 active index 变化后不得命中旧结果。

当前状态：

- 数据表支持 `retrieval_result` 类型。
- 查询链路未实现读写。

### 5.4 final answer 缓存

当前版本不允许启用最终答案缓存。

原因：

- 最终答案同时受权限、引用、模型、prompt、上下文、降级状态和用户身份影响。
- citation 校验失败、权限收紧、文档删除或 access block 变化都可能让旧答案变成不安全内容。
- 当前配置 schema 明确要求 `final_answer_enabled=false`。

## 6. Redis key 设计约束

当前代码没有实际 Redis key。后续接入 Redis 时，key 设计必须与 `query_cache_entries` 的维度一致。

最低要求：

- 包含企业 ID。
- 包含缓存对象类型。
- 包含权限过滤 hash。
- 包含请求过滤 hash。
- 包含知识库范围 hash。
- 包含 query hash。
- 包含 active config version。
- 包含 permission version。
- 包含 active index version hash。
- 包含模型路由 hash。
- 涉及 prompt 的结果必须包含 prompt template version。

最终答案如果未来开放，也必须包含 user_id，并继续禁止跨用户复用，除非权限模型和引用校验能力另行重构。

## 7. 权限版本和索引版本如何进入缓存

当前数据库账本已经为缓存预留：

- `permission_version`
- `permission_filter_hash`
- `index_version_hash`

后续缓存实现必须使用这些字段隔离不同权限和索引状态。

必要规则：

- 用户权限变化后，旧 `permission_version` 的缓存不得命中。
- 文档权限收紧后，必须依赖 access block 或权限版本变化阻断旧缓存。
- active index version 变化后，旧 `index_version_hash` 的检索结果不得复用。
- 配置版本变化后，旧 `config_version` 的结果不得复用。

## 8. 权限收紧如何失效

当前系统的权限收紧安全边界不是缓存失效，而是 fail closed：

- 文档删除和权限收紧会写 access block。
- 查询候选进入上下文前会做权限过滤和状态过滤。
- citation 读取会重新做权限校验。

后续接入缓存后，缓存失效也必须服务于这个边界：

- 先写 access block，再异步刷新索引或清理缓存。
- 旧缓存命中后仍要检查 access block。
- retrieval result 缓存只保存候选摘要，不应绕过 source 和 citation 二次校验。
- 不能用前端清空列表替代后端缓存失效。

## 9. 哪些结果不能缓存

当前系统尚未实现业务缓存；如果未来接入，下列结果不得缓存：

- citation unauthorized 的答案。
- citation invalid 且未安全修复的答案。
- 降级不完整或上下文为空的最终答案。
- LLM provider 超时或 HTTP 错误生成的降级答案。
- 权限过滤中、索引刷新中或 access block 命中的结果。
- draft index、deleted document、blocked document、archived index 相关结果。
- 包含 secret、token、完整 prompt、文档原文或未脱敏敏感信息的内容。

query embedding 和 retrieval result 可以独立评估，但仍必须携带权限、配置、索引和模型版本维度。

## 10. Redis 不可用时的当前行为

当前行为：

- Redis 是 ServiceBootstrap 检查项。
- Redis 不可用时，ready 不通过。
- 业务 API 可能被 setup guard 拒绝。
- 系统不会自动降级为“无业务缓存运行”。

如果后续要实现 Redis 不可用时无缓存运行，需要调整：

- active config 中 Redis 是否 required 的语义。
- ServiceBootstrap 的 Redis 检查级别。
- 缓存 client 的失败处理。
- 查询链路对缓存 miss、Redis timeout、Redis unavailable 的处理。
- 日志和审计中对“无缓存运行”的标记。

当前代码尚未实现这些调整。

## 11. 当前边界

- Redis 已接入基础设施和配置校验，但未承载业务缓存。
- `query_cache_entries` 是预留账本，不代表查询缓存已上线。
- 最终答案缓存被当前配置 schema 禁止。
- Redis 不可用时无缓存降级尚未实现。
- 任何缓存实现都不能绕过 Permission Service、access block、citation 校验和文档状态过滤。

# Little Bear 后端架构设计书

更新时间：2026-06-02

本文基于当前代码实现整理，描述 `apps/api` 与 `apps/worker` 的真实后端架构、模块边界、核心链路和运行约束。本文作为后续后端开发和评审的当前成熟架构依据。

## 1. 架构定位

Little Bear 后端是一个“模块化单体 API + 轻量 Worker”的企业内部 RAG 系统后端。API 进程负责 HTTP 入口、认证、权限、配置、知识库管理、查询和诊断；Worker 进程复用 API 内的导入与索引服务，从 PostgreSQL 领取导入任务并推进 parse、clean、chunk、embed、index、publish 等阶段。

当前后端不把所有问题交给大模型处理。PostgreSQL 是事实源，Redis、Qdrant、MinIO 和模型 provider 都是运行时外部依赖或派生状态；权限、状态机、索引发布、查询日志和审计均由后端显式控制。

    dependencies/            认证、request_id / trace_id 等 FastAPI 依赖

  modules/
    setup/                   首次初始化、恢复初始化、setup token、bootstrap

## 3. 分层边界

后端依赖方向按当前实现保持单向：

```text
api/routes
  -> api/dependencies / api/schemas / api/presenters
  -> modules/<domain> service/facade

modules/<domain> service/facade
  -> repository / policy / runtime / writer / shared / db

runtime
  -> ConfigService / SecretStore / adapters / model clients / storage

adapters
  -> 外部系统协议
```

各层职责如下：

- `api/routes`：只负责 HTTP 参数、认证、分页、调用 service、错误响应。管理、配置、导入和查询路由中存在聚合 route 文件，但聚合文件只用于 `include_router` 和导出已有名称，不承载业务规则。
- `api/schemas`：定义请求和响应 DTO，不参与业务计算。
- `api/presenters`：裁剪展示字段，把 service 模型转换成前端需要的响应结构。
- `modules/<domain>`：负责业务规则、事务编排、权限校验、状态变更和运行时调用。
- `repository` / `reader` / `writer`：集中 SQL 读写，不构造 API 响应。
- `runtime.py`：从 active config 和 Secret Store 组装对象存储、Qdrant、embedding、rerank、LLM 等 adapter。
- `shared`：只放无业务归属的通用能力。

## 4. 启动生命周期

API 入口位于 `apps/api/app/main.py`：

1. `create_app()` 加载进程级 settings，配置日志。
2. 注册 `RequestContextMiddleware`，为每个请求写入 `request_id` 和 `trace_id`。
3. 注册 `SetupGuardMiddleware`，拦截未初始化、迁移缺失、active config 缺失、bootstrap 未就绪的业务请求。
4. `lifespan()` 默认执行 `SetupStartupService().run()`。
5. `include_api_routes()` 注册健康检查、setup、auth、config、admin、knowledge、import、query、audit、permission 路由。

启动层只允许读取数据库连接和少量进程运行参数。业务配置不从 `.env` 直接读取，而是在初始化后通过 `ConfigService` 从 PostgreSQL active config 加载。

Setup 启动判定逻辑：

- 数据库未配置或不可达：进程启动失败。
- migration 缺失或 system_state 表不可读：进入 `migration_required`，业务接口由 setup guard 拒绝。
- 未初始化：签发 setup JWT，开放 setup 相关接口。
- 已初始化但 active config 缺失且可恢复：进入 recovery setup。
- 已初始化且 active config 存在：执行 ServiceBootstrap，确认关键外部依赖和配置可用。

## 5. 配置与密钥

配置事实源是 PostgreSQL 中的 config 相关表和 `system_state.active_config_version`。`ConfigService` 是业务模块读取配置的统一入口，内部拆分为：

- `ConfigReader`：读取并校验 active config。
- `ConfigVersionService`：配置版本列表、新建、编辑、归档、草稿保存。
- `ConfigPublisher`：激活配置版本并刷新缓存。
- `ConfigDependencyValidator`：执行 schema 和依赖探测。
- `ConfigCache`：进程内 active config 缓存。

配置 schema 当前从 `docs/contracts/config.schema.json` 加载。`docs/contracts/` 是当前成熟契约源。

Secret 处理原则：

- 初始化 payload 中的 provider token 只短暂停留在请求体，随后写入 Secret Store。
- Auth、storage、indexing、query runtime 只使用 secret ref 读取密钥，不在日志和 API 响应中展示 secret value。
- 模型 provider、MinIO、Qdrant API key 均通过 runtime factory 按需读取。

## 6. 数据库与事务

PostgreSQL 是后端事实源。数据库连接在 `apps/api/app/db/session.py` 中集中创建：

- `get_engine()` 使用 SQLAlchemy `create_engine` 和 `pool_pre_ping=True`。
- `session_scope()` 提供同步事务边界：正常退出提交，异常退出回滚。
- API 路由和 Worker 都通过 session 或 `session_scope()` 明确控制事务。

核心表由 `apps/api/migrations/versions` 管理。当前迁移链已压缩为
`0013_current_schema_baseline.py`，revision 仍为 `0013_query_log_scope_summary`：

- 空库执行 `db-upgrade` 时一次性建立当前版本 Schema。
- 已经升级到 `0013_query_log_scope_summary` 的现有数据库不会重复执行建表。
- 仍停留在旧增量链中间版本的历史数据库，应先使用旧迁移链升级到 head，或重建数据库后执行当前基线迁移。

当前基线迁移覆盖：

- `system_state`：初始化状态、active config 指针、bootstrap 状态。
- `config_versions` / `system_configs`：配置版本和配置内容。
- `users`、`credentials`、`jwt_tokens`、`departments`、`roles`、`role_bindings`：认证、组织和 RBAC。
- `knowledge_bases`、`folders`、`documents`、`document_versions`、`chunks`：知识库和文档事实源。
- `permission_snapshots`、`knowledge_base_accesses`、`access_blocks`：权限快照、知识库访问和 fail-closed 阻断。
- `index_versions`、`chunk_index_refs`、`keyword_index_entries`：索引账本。
- `import_jobs`：导入 Worker 任务事实源。
- `audit_logs`、`query_logs`、`model_call_logs`：审计、查询诊断、模型调用诊断。
- `query_conversations`、`query_messages`：普通用户查询页面会话与消息。
- `query_retrieval_diagnostics`：查询链路检索诊断摘要。

## 7. API 入口

当前 API 统一使用 `/internal/v1` 前缀；管理后台接口使用 `/internal/v1/admin`。

主要入口：

- Health：`/health/live`、`/health/ready`。
- Setup：setup-state、setup-config-validations、setup-initialization。
- Auth：sessions、token-refreshes、users/me、用户自助密码修改。
- Config Admin：configs、config-versions、config-validations。
- Admin：departments、users、roles、knowledge-bases、folders、documents、index-health、snapshots、index rebuild。
- Knowledge User：knowledge-bases、folders、documents、chunks、source preview。
- Import：document-imports、upload document imports、import-jobs、admin import-jobs。
- Query：queries、query-streams、query-conversations。
- Audit / Diagnostics：audit-logs、query-logs、model-call-logs。
- Permissions：知识库和文档权限更新。

错误响应统一使用结构化格式：

```json
{
  "request_id": "req_xxx",
  "error_code": "SOME_ERROR",
  "message": "human readable message",
  "stage": "route_or_service_stage",
  "retryable": false,
  "details": {}
}
```

## 8. 认证与会话

认证模块以 `AuthService` 为门面，内部拆分为：

- `PasswordService`：argon2 密码哈希和校验。
- `SessionService`：登录、刷新、退出编排。
- `TokenService`：JWT 签发、校验、数据库 token 账本、撤销。
- `UserContextLoader`：当前用户、部门、角色和 scopes 上下文加载。
- `CredentialService`：密码修改、凭据状态更新。

JWT 实现已使用 PyJWT。项目保留 `app.shared.jwt.encode_hs256/decode_hs256` 作为内部 API，内部限定 HS256、校验 `exp`、`iss`、`aud`、`token_type`，并把 PyJWT 异常映射为项目内 `JwtError`。

JWT 不是无状态裸 token。每个 access / refresh token 都会写入 `jwt_tokens` 表，认证时同时校验：

- token 签名和必要 claims。
- token type。
- subject user、enterprise。
- `jwt_tokens.status`。
- 过期时间。
- required scope。

## 9. 权限模型

权限由 RBAC scope、知识库访问控制和文档可见性共同组成。

`PermissionService` 是查询和管理侧权限判断的核心门面，内部拆分为：

- `PermissionContextLoader`：加载用户、企业、部门、角色、scope、permission_version。
- `PermissionFilterBuilder`：构建 Qdrant payload filter、关键词 SQL where、metadata SQL where。
- `PermissionPolicyValidator`：校验 visibility policy 和权限快照 payload。
- `PermissionCandidateGate`：对召回候选做二次准入。

知识库权限和文档权限是两层边界：

- 知识库通过 `kb_visibility` 和 `knowledge_base_accesses` 控制是否可发现、可查询、可管理。
- 文档通过 `visibility`、`owner_department_id`、`permission_snapshot_id` 和 access block 控制是否可进入上下文。

查询候选必须同时满足：

- 企业匹配。
- 知识库可访问。
- 文档 active 且 indexed。
- chunk active。
- chunk index ref active。
- index version active。
- 不存在有效 access block。
- 权限版本不落后，或完成当前权限上下文校验。

## 10. 管理后台后端

管理域以 `AdminService` 为 route-facing facade。它不再通过历史 `core.py` 中间文件转发，而是直接组合各业务服务和 mixin：

- `AdminUsersService`：用户列表、创建、编辑、删除、锁定、密码重置、用户部门绑定。
- `AdminDepartmentsService`：部门列表、选项、创建、编辑、删除。
- `AdminRolesService`：角色列表、可分配角色、用户角色绑定。
- `AdminKnowledgeBasesService`：知识库列表、选项、创建、编辑、删除。
- `AdminFoldersService`：文件夹列表、创建、编辑、删除。
- `AdminDocumentsService`：文档列表、详情、版本、chunk、预览、编辑、删除。
- `AdminPermissionService`：知识库和文档权限更新。
- `AdminIndexOpsService`：文档重建、知识库重建、collection 重建、索引清理任务。

管理接口仍必须通过后端权限校验。前端菜单隐藏只作为用户体验，不作为权限边界。

## 11. 导入与 Worker

导入链路由 API 创建任务，Worker 异步推进任务。

API 创建导入任务：

```text
认证与权限校验
-> 上传文件或 URL / metadata item 校验
-> 写 document / document_version / import_job
-> 原始文件写入对象存储
-> 返回 import_job
```

Worker 进程入口是 `apps/worker/app/main.py`。它通过 `build_import_service(session)` 复用 API 内的 ImportService，循环执行：

```text
claim_next_job
-> heartbeat_claimed_job
-> advance_claimed_job
-> stage effect
-> mark_claimed_job_failed on ImportServiceError
```

导入阶段：

```text
validate -> parse -> clean -> chunk -> embed -> index -> publish -> cleanup -> finished
```

重要实现点：

- `import_jobs` 是任务事实源。
- `locked_by` / `locked_until` 用于 Worker 接管和崩溃恢复。
- Worker claim 会领取可运行的 `queued` / `retrying` 任务，也会接管 `locked_until` 已过期的 `running` 任务；接管后保持原阶段继续推进，避免崩溃 Worker 留下永久运行中任务。
- retryable 失败会把任务置为 `retrying`、清空锁并写入 `next_retry_at`；下一 Worker 只能在重试时间到达后重新领取。
- `idempotency_key` 用于 API 侧幂等。
- Parser 会输出 `ParsedBlock` 结构块，覆盖 heading、paragraph、list_item、table、code 和 page_break；clean 阶段保留清洗后的 blocks，chunk 阶段由 `StructureAwareChunker` 消费 blocks。
- `StructureAwareChunker` 会按 heading path 聚合段落和列表项，table / code 单独成块，超长段落优先按句子切分；chunk 会写入 `heading_path`、`page_start/page_end`、`source_offsets.block_start/block_end`、`block_types`、`section_id`、`chunk_strategy` 和 `chunker_version`。
- 解析、清洗、chunk 全文通过对象存储保存；数据库保存 object key、自然正文 preview、页码、结构化 source_offsets、hash 和索引账本。
- `permission_refresh` 任务在 index 阶段刷新 Qdrant payload。

## 12. 索引服务

`IndexingService` 是索引 facade，内部拆分为：

- `DraftIndexService`：创建 draft index version、生成 draft vector point。
- `IndexPublishService`：校验并发布 active index version。
- `IndexCleanupService`：清理 pending delete index 和向量点。
- `PermissionPayloadRefreshService`：权限变更后的 payload 刷新。

`build_indexing_service(session)` 按 active config 构建真实运行时：

- 从配置读取 Qdrant base URL、collection prefix、embedding model、embedding dimension。
- 从配置读取 `import.embedding_batch_size`，用于控制索引写入时的 embedding 批量大小。
- 从 Secret Store 读取 Qdrant API key 和 embedding provider token。
- 创建 `ModelGatewayEmbeddingClient`。
- 创建 `QdrantVectorIndexWriter` adapter。

`QdrantVectorIndexWriter` 会先调用 embedding provider 生成向量，再写入 Qdrant draft point。为适配 TEI / OpenAI-compatible provider 的 batch 限制，writer 会按配置分批处理；当某个 embedding 批次被 provider 拒绝或超时且批次大于 1 时，会二分拆小后重试，避免单个大文档一次产生过多 chunk 时直接卡死在 index 阶段。

索引发布遵循 draft -> active 思路：draft vector point 和 draft index version 在发布前不应被查询命中；发布阶段负责激活向量点、写 active index version、更新文档 index_status。

关键词索引和向量索引的检索文本使用结构化摘要：

```text
title: 文档标题
section: 一级标题 / 二级标题
content: chunk 正文预览
```

自然 chunk 正文仍通过对象存储和 `chunks.text_preview` 供 citation、上下文和管理端预览使用，避免把索引增强前缀展示给最终用户。

## 13. 查询服务

查询服务分为普通查询和 SSE 流式查询。`QueryService` 是 route-facing facade，真正编排在 `QueryOrchestrator`。

查询计划构建：

```text
normalize query
-> load active config version
-> build PermissionContext
-> require_queryable_knowledge_bases
-> load active index versions
-> QueryRewriteService.rewrite
-> build PermissionFilter
-> keyword search for each rewritten query
-> vector search for each rewritten query
-> Weighted RRF fusion
-> candidate gate
-> rerank
-> relevance gate
-> quality gate
-> neighbor expansion
-> document / section limit and MMR
-> build QueryContext
```

P3 第一阶段后，检索候选会携带 `matched_query`、`matched_query_index`、`query_weight`、`source_weight` 和 `source_score`。融合公式使用 `query_weight * source_weight / (rrf_k + rank)`，默认让原始问题和向量召回略高于 rewrite query 和关键词召回。

关键词检索会对标题、`heading_path` 和 tags 命中加权；rerank 成功时由 rerank score 做相关性门控，rerank 未配置或降级时由 `CandidateQualityGate` 使用融合分和原始召回分做兜底质量门控。质量门控失败会写入 `query.quality_gate_failed` 审计事件，不把低质量候选交给 LLM。

P3 第二阶段后，答案模式会对已通过权限 gate 的候选做相邻 chunk 扩展。扩展 chunk 必须重新经过 Permission Service candidate gate，且仍需满足文档状态、chunk 状态、active index、`chunk_index_refs.visibility_state` 和 access block 校验。Context Builder 会按文档和 section 限制 chunk 数量，并使用轻量 MMR 去冗余，避免同一文档同一小节挤占全部上下文。最终选入上下文的 chunk 会优先按 `text_object_key` 从对象存储读取完整正文；对象不可用时回落到 `text_preview`，并继续执行上下文预算截断。

查询日志写入时会同步写入 `query_retrieval_diagnostics`，记录 rewrite query 摘要、召回/融合/门控阶段数量、quality gate 摘要和最终上下文 chunk 摘要。该表不保存完整 query 明文、完整 prompt 或文档原文。

答案生成：

```text
QueryContext
-> AnswerService.generate / AnswerService.stream
-> LLM provider
-> strip <think> blocks and source ref display noise
-> citation validation
-> finalize query result
-> query_logs / model_call_logs / audit_logs
```

当前多轮会话用于前端展示和历史同步；Query Rewrite 可读取最近会话消息做省略指代补全，但只影响检索 query 生成。Context Builder、rerank query 和最终答案生成仍以用户本轮原始问题为主，不把历史回答当作事实来源。

查询降级策略：

- active config 或向量运行时不可用：向量召回降级，保留关键词闭环。
- embedding / Qdrant 不可用：向量召回降级。
- rerank 不可用：使用融合分数结果。
- context 为空：返回结构化降级答案，说明缺少可用资料。
- LLM 不可用：返回降级答案和可用引用。
- citation 校验失败：抑制或降级最终答案，避免无授权或不可验证引用进入用户响应。

所有降级需要进入响应、query log、model call log 或 audit 摘要。

## 14. 模型与外部适配器

模型调用统一通过 `modules/models`：

- `ModelGatewayEmbeddingClient`：embedding provider。
- `ModelGatewayRerankClient`：rerank provider。
- `ModelGatewayChatClient`：OpenAI-compatible chat completions。
- `post_json` / `post_stream_lines`：共享 HTTP transport。

HTTP transport 会：

- 使用 Bearer token。
- 设置 JSON 或 SSE accept header。
- 将 HTTPError、URLError、TimeoutError、OSError 转成 `ModelClientError`。
- 限制 provider error body 截断长度。

Qdrant 适配器位于 `apps/api/app/adapters`，通过 `QdrantVectorRetriever` 和 `QdrantVectorIndexWriter` 支撑查询和索引写入。

对象存储通过 `ObjectStorage` 协议抽象。当前实现包括：

- `InMemoryObjectStorage`：测试和本地最小实现。
- `MinioObjectStorage`：使用 AWS Signature V4 的 path-style 最小实现。

## 15. 审计与可观测性

后端观测数据主要来自：

- request headers：`x-request-id`、`x-trace-id`。
- `audit_logs`：高风险操作、setup、配置、权限、索引、查询异常。
- `query_logs`：query hash、kb_ids、状态、降级、配置版本、权限版本、索引版本 hash、延迟、候选数、引用数。
- `model_call_logs`：模型类型、模型名、调用方、路由 hash、耗时、token 摘要、输入/输出 hash、错误码。

日志和审计不保存 secret value、完整 token、完整 prompt 或文档原文。模型调用日志只记录 hash 和摘要字段。

## 16. Worker 与 API 的区别

API 是同步请求入口，负责创建任务、查询任务状态、执行查询和管理操作。

Worker 是后台任务执行器，不暴露 HTTP 接口。它只做导入任务推进：

- 轮询 `import_jobs`。
- 抢占可运行任务。
- 维护任务锁和心跳。
- 执行 parse、clean、chunk、embed、index、publish。
- 失败时写错误码、retryable 和下一次重试时间。

多个 Worker 可以并行运行，依靠 `locked_by` 和 `locked_until` 避免同一任务被重复执行。
非持锁 Worker 推进任务会被 `IMPORT_JOB_LOCK_REQUIRED` 拒绝；持锁 Worker 心跳续约，锁过期后允许其他 Worker 接管。

## 18. 当前实现边界

以下是当前代码实现的实际边界，不应在后续需求中误判为已经完成的高级能力：

- Worker 是 PostgreSQL 轮询式任务执行器，尚未引入独立消息队列。
- 查询多轮会话已保存和展示；P1 Query Rewrite 可读取最近历史消息做省略指代补全，P3 已实现候选级 matched query 归因，但尚未实现长历史总结或跨轮意图规划。
- 成熟契约已迁入 `docs/contracts/`；运行时配置 schema 和 OpenAPI 契约测试均读取该目录。
- `ConfigService` 仍保留少量私有兼容委托，主要用于既有测试和扩展 patch 点；主业务职责已经拆到 reader、repository、publisher、version_service。
- MinIO 当前是最小 SigV4 实现，不包含 multipart 上传、复杂重试和 presigned URL。
- 模型 provider 以 HTTP / OpenAI-compatible / TEI 风格适配为主，未实现统一在线模型目录或多 provider 自动路由。
- Redis 已作为基础设施存在，但当前后端核心查询、导入和权限闭环主要依赖 PostgreSQL、Qdrant、MinIO 和模型 provider。

## 19. 后续开发约束

新增后端功能时应遵守：

- route 不直接写复杂 SQL，不直接调用 Qdrant、MinIO 或模型 provider。
- 业务配置只通过 `ConfigService` active config 获取。
- 高风险写操作必须写审计。
- 权限收紧、删除、索引刷新必须 fail closed。
- 查询候选进入 LLM 上下文前必须完成权限过滤和候选二次 gate。
- 列表接口必须后端分页、后端筛选、后端权限过滤，只返回列表展示字段。
- 外部 IO 不应长时间占用数据库事务。
- 新增接口同步维护 API schema、presenter、权限 scope、错误码、测试和契约文档。

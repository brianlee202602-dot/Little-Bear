# 权限模型设计书

更新时间：2026-06-03

本文说明 Little Bear 当前权限系统如何工作。它关注业务权限边界，不重复接口权限矩阵中的逐接口 scope 列表。

## 1. 权限模型总览

当前权限由两层共同决定：

1. RBAC scope：决定用户能否调用某类能力，例如查询、用户管理、知识库管理、审计查看。
2. 资源可见性：决定用户能否访问某个知识库或文档，例如知识库可见性、知识库访问规则、文档可见性和部门归属。

两者必须同时满足。拥有接口 scope 不代表拥有所有资源；能看到知识库也不代表能读取其中所有文档。

## 2. 权限上下文

`PermissionService.build_context` 从数据库构建 `PermissionContext`。

上下文包含：

- `enterprise_id`
- `user_id`
- 用户状态
- 用户部门列表
- 用户角色列表
- 角色 scope 合并结果
- 企业 `org_version`
- 企业 `permission_version`
- `permission_filter_hash`
- `request_id`

构建时会检查：

- 用户存在且未删除。
- 用户 `status=active`。
- 企业 `status=active`。
- 部门成员关系 active。
- 角色绑定和角色 active。

## 3. RBAC Scope

RBAC scope 来自：

- 基础用户 scope：`auth:session`、`auth:password:update:self`。
- 用户 active role bindings 中角色的 `scopes`。

`PermissionContext.has_scope` 支持：

- 精确 scope，例如 `rag:query`。
- 模块通配，例如 `knowledge_base:*`。
- 全局通配 `*`。

scope 只回答“能否执行某类动作”，不回答“能否操作某个资源”。

## 4. 知识库可见性

知识库是检索容器。当前 `knowledge_bases.kb_visibility` 支持：

| 值 | 含义 | 查询判定 |
| --- | --- | --- |
| `enterprise` | 企业内可发现、可选择 | 具备查询 scope 的企业内用户可进入知识库候选范围 |
| `department_acl` | 指定访问对象可见 | 需要命中 `knowledge_base_accesses` 中 active access rule |
| `private` | 私密知识库 | 需要命中 active access rule，创建时会给 owner department 补齐基础访问规则 |

`knowledge_base_accesses.permission` 支持：

- `discover`：可发现。
- `query`：可用于问答检索。
- `manage`：可管理，且隐含 discover/query。

访问对象支持：

- `department`
- `user`
- `role`

## 5. 文档可见性

文档可见性由 `documents.visibility` 和 `documents.owner_department_id` 决定。

当前文档可见性支持：

| 值 | 含义 |
| --- | --- |
| `enterprise` | 企业内可读，前提是用户能查询父知识库 |
| `department` | 仅文档 owner department 内用户可读，前提是用户能查询父知识库 |

这意味着：

- 知识库可见性控制“能不能发现/选择这个容器”。
- 文档可见性控制“容器内某个文档能不能被读入上下文”。
- 用户看到知识库，但不一定能看到该知识库内所有文档。

## 6. 管理角色边界

### 6.1 系统管理员

系统管理员通常具备全局管理 scope 和跨知识库管理能力。后端仍会对具体接口执行权限检查。

### 6.2 部门管理员

部门管理员可以管理本部门范围内的用户和相关资源。创建用户、绑定部门、导入文档时，后端会限制不能越权操作其他部门。

### 6.3 知识库管理员

知识库管理员可以管理被授权的知识库。当前管理链路支持让知识库管理员对指定知识库执行文档导入、文档管理和索引相关操作。

知识库管理员不是自动拥有全企业所有文档读取权。它的管理边界来自：

- RBAC scope。
- actor context 中的 `knowledge_base_ids`。
- `knowledge_base_accesses` 中的 manage 权限。

### 6.4 普通员工

普通员工可以登录查询前端并查询有权限的知识库和文档。普通员工不能登录管理后台。

## 7. 查询权限过滤

查询链路有三层权限控制。

### 7.1 知识库范围解析

如果请求传入 `kb_ids`，后端通过 `require_queryable_knowledge_bases` 校验这些知识库是否可查询。

如果请求不传 `kb_ids`，后端通过 `list_queryable_knowledge_base_ids` 自动列出当前用户所有可查询知识库，形成 `auto_all_accessible` 查询范围。

### 7.2 召回阶段过滤下推

`PermissionFilterBuilder.build_filter` 会为向量召回、关键词召回和元数据查询构造统一权限过滤条件。

过滤条件包括：

- enterprise 匹配。
- 知识库范围。
- active index version 范围。
- document active。
- document indexed。
- chunk active。
- visibility_state active。
- 文档 `enterprise` 可见，或 `department` 可见且 owner department 属于当前用户部门。
- 不存在 active access block。

向量召回通过 Qdrant payload filter 下推；关键词召回通过 SQL where 条件下推。

### 7.3 Candidate Gate 二次校验

召回后，`PermissionCandidateGate` 会对候选再次校验：

- enterprise 必须匹配。
- 不允许 active access block。
- 候选知识库必须在请求解析后的 allowed_kb_ids 内。
- index version 必须属于 active index versions。
- `visibility_state` 必须 active。
- document lifecycle 必须 active。
- document index_status 必须 indexed。
- chunk status 必须 active。
- 文档可见性必须匹配企业或当前用户部门。

二次校验失败的候选不会进入 rerank、context builder 或 citation。

## 8. 权限收紧与 Fail Closed

权限收紧场景包括：

- 文档从 `enterprise` 改为 `department`。
- department 文档 owner department 改变。
- 知识库可见性从更宽范围改为更窄范围。
- 删除知识库、文件夹、文档或 chunk。

处理原则：

1. 先更新 PostgreSQL 事实源。
2. 递增企业 `permission_version`。
3. 写入新的 `resource_policies` 或 `permission_snapshots`。
4. 如果是权限收紧，先写 active `access_blocks`。
5. 创建 `permission_refresh` import job。
6. Worker 刷新 keyword / vector payload。
7. 刷新完成后释放对应 access block。

因此，权限收紧到索引 payload 刷新完成之间，旧索引不会继续命中。

## 9. 删除与阻断

删除不是只依赖物理删除。当前系统通过状态和 access block 共同保证查询安全：

- `documents.lifecycle_status=deleted` 不允许查询。
- `documents.deleted_at` 参与管理列表和资源读取过滤。
- `chunk_index_refs.visibility_state` 可进入 blocked/deleted 状态。
- `access_blocks` 可以按 knowledge base、folder、document、chunk 阻断查询或 citation。

查询链路和 citation 校验都必须检查 active access block。

## 10. 管理后台菜单不是权限边界

前端会根据当前用户能力隐藏缺少权限的菜单，但这只是用户体验优化。

真正权限边界在后端：

- 每个接口检查 JWT。
- 每个管理接口检查 scope。
- 涉及资源时检查部门作用域、知识库作用域或具体 access rule。
- 详情接口必须重新校验权限，不能因为列表可见就默认详情可见。

## 11. 常见误解

### 11.1 为什么能看到知识库，却查不到某些文档？

因为知识库可见性和文档可见性是两层边界。用户能查询知识库，只代表这个容器可进入检索范围；其中 `department` 文档仍要求用户属于文档 owner department。

### 11.2 为什么权限刚收紧后旧索引不能继续命中？

因为权限收紧会先写 active access block。即使 Qdrant payload 还没刷新，召回后的二次 gate 和 SQL access block 检查也会 fail closed。

### 11.3 为什么模型不能参与权限判断？

模型输出不稳定且不可审计。权限必须由 PostgreSQL 事实源、Permission Service、索引 payload 和 candidate gate 共同决定。

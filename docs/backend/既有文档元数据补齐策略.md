# 既有文档元数据补齐策略

本文说明结构化切块上线后，已经导入过的既有业务文档如何获得新的 chunk 元数据。当前策略基于现有实现，不假设旧数据可以无损反推结构。

## 适用范围

新导入或重新导入文档会经过当前导入链路：

```text
parse -> clean -> StructureAwareChunker -> chunks -> keyword/vector index
```

生成的 chunk 会自动写入：

- `chunks.heading_path`
- `chunks.page_start`
- `chunks.page_end`
- `chunks.source_offsets.block_start`
- `chunks.source_offsets.block_end`
- `chunks.source_offsets.block_types`
- `chunks.source_offsets.heading_path`
- `chunks.source_offsets.section_id`
- `chunks.source_offsets.chunk_strategy`
- `chunks.source_offsets.chunker_version`
- `chunks.token_count`

这些字段会随 chunk 一起进入后续索引文本、citation 定位和查询诊断。

## 不做的事情

当前不对既有 `chunks` 做批量原地回写。

原因是旧 chunk 只保留了 preview、旧切块边界和有限 offsets，无法可靠恢复标题层级、页码跨度、结构块范围和段落边界。强行回写会制造看似完整但不可验证的元数据，后续 citation 和权限审计会被污染。

## 正确补齐路径

既有业务文档需要补齐结构化元数据时，使用以下路径之一：

1. 重新上传或重新导入该文档。
2. 使用后续文档版本级重建能力生成新的 `document_version`。

这两种路径都会重新解析原文并重新切块，因此能生成可信的结构化元数据。

## 重建索引的边界

管理后台的“重建索引”用于把现有 active 文档或现有 chunk 重新写入 keyword / vector 索引。它不会重新解析原始文档，也不会改变已有 chunk 的切分边界或补齐缺失的结构化 `source_offsets`。

因此：

- 只需要刷新索引 payload、embedding 或 collection 状态时，使用重建索引。
- 需要补齐页码、标题路径、结构块 offsets 或 chunker 版本时，必须重新导入或生成新文档版本。

## 验证方式

当前代码通过导入链路测试验证新导入文档会自动补齐结构化元数据：

```bash
PYTHONPATH=apps/api .venv/bin/python -m pytest -q tests/unit/test_import_executors.py tests/unit/test_import_service.py
```

关键断言包括：

- Markdown heading 能传播到 `heading_path` 和 `section_id`。
- PDF / 带页码 block 能传播 `page_start` / `page_end`。
- chunk 写库时包含 `chunk_strategy=structure_aware` 和当前 `chunker_version`。

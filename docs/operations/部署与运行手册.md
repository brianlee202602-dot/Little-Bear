# Little Bear 部署与运行手册

更新时间：2026-06-03

本文用于指导开发人员在本地或内部开发环境部署、初始化、运行和验收 Little Bear。本文按当前代码实现编写，不描述尚未落地的生产编排能力。

## 1. 适用范围

本文覆盖：

- 本地基础设施启动。
- 数据库迁移。
- API、Worker、普通查询前端和管理后台启动。
- 系统初始化。
- 文档导入与查询验证。
- 常见故障排查。

本文不覆盖：

- Kubernetes / Helm 生产编排。
- API、Worker、前端镜像构建流水线。
- Redis 业务缓存接入方案。
- 多副本高可用部署细节。
- 云厂商托管服务的账号、网络和安全组配置。

当前仓库的部署入口以 `Makefile` 为准。

## 2. 组件说明

| 组件 | 路径 / 服务 | 作用 |
| --- | --- | --- |
| API | `apps/api` | FastAPI 后端，提供初始化、认证、管理后台、导入、查询和诊断接口 |
| Worker | `apps/worker` | 消费 `import_jobs`，执行文档解析、切块、embedding、索引写入和发布 |
| 普通查询前端 | `apps/web` | 普通用户知识库问答页面 |
| 管理后台 | `apps/admin` | 初始化、配置、用户、部门、知识库、导入、诊断和审计管理 |
| PostgreSQL | `docker-compose.yml` | 业务事实源、配置、权限、任务、日志和索引账本 |
| Redis | `docker-compose.yml` | 当前作为 bootstrap 外部依赖检查项；业务缓存尚未接入 |
| MinIO | `docker-compose.yml` | 原始文件、解析结果、清洗结果和完整 chunk 对象存储 |
| Qdrant | `docker-compose.yml` | chunk 向量索引 |
| TEI embedding / rerank | `docker-compose.yml` | 本地演示用 embedding / rerank provider，可替换为外部服务 |

默认端口：

| 服务 | 默认地址 |
| --- | --- |
| API | `http://localhost:8000` |
| 普通查询前端 | `http://localhost:5173` |
| 管理后台 | `http://localhost:5174` |
| PostgreSQL | `localhost:5432` |
| Redis | `localhost:6379` |
| MinIO API | `http://localhost:9000` |
| MinIO Console | `http://localhost:9001` |
| Qdrant HTTP | `http://localhost:6333` |
| TEI embedding | `http://localhost:8081` |
| TEI rerank | `http://localhost:8082` |

## 3. 环境要求

建议环境：

- Python `>=3.12`。
- Node.js 和 npm，版本以 `package.json` / lockfile 能正常安装为准。
- Docker 与 Docker Compose。
- 可访问模型 provider。如果使用本地 TEI embedding / rerank，需要能拉取对应镜像。
- PostgreSQL 扩展镜像使用 `zhparser/zhparser`，不要替换为普通 PostgreSQL 镜像，除非自行安装 `zhparser`。

安装依赖后，建议先确认命令可用：

```bash
.venv/bin/python --version
npm --version
docker compose version
```

## 4. 环境文件

首次启动前生成本地环境文件：

```bash
make env
```

该命令仅在 `.env` 不存在时从 `.env.example` 复制，不会覆盖已有 `.env`。

`.env` 只保存本地进程启动参数和基础设施初始化参数。业务配置不应直接依赖 `.env`，包括 Redis、MinIO、Qdrant、embedding、rerank、LLM、安全、检索、缓存、限流和审计策略。这些业务配置必须通过初始化流程写入 PostgreSQL，并由 active config 驱动运行。

本地必须重点检查：

```bash
DATABASE_URL=postgresql+psycopg://little_bear:little_bear_dev@localhost:5432/little_bear
SECRET_STORE_MASTER_KEY=<强随机值>
SECRET_INIT_MINIO_ACCESS_KEY=minioadmin
SECRET_INIT_MINIO_SECRET_KEY=minioadmin
SECRET_INIT_JWT_SIGNING_KEY=<强随机值>
VITE_API_BASE_URL=http://localhost:8000
```

`SECRET_STORE_MASTER_KEY` 用于加密 PostgreSQL `secrets` 表中的密钥值。生产或长期开发库不得丢失，否则已写入的 secret 无法解密。

生成随机值示例：

```bash
openssl rand -base64 64
```

## 5. 启动基础设施

启动 Docker Compose 基础设施：

```bash
make up
make ps
```

查看日志：

```bash
make logs
```

停止基础设施：

```bash
make down
```

删除本地 volume 并重置所有数据：

```bash
make reset
```

`make reset` 会删除 PostgreSQL、Redis、MinIO、Qdrant 和 TEI 数据卷，只能用于本地开发环境。

## 6. 数据库迁移

PostgreSQL ready 后执行迁移：

```bash
make PYTHON=.venv/bin/python db-upgrade
make PYTHON=.venv/bin/python db-current
```

当前迁移已压缩为当前 schema 基线：

```text
apps/api/migrations/versions/0013_current_schema_baseline.py
revision = "0013_query_log_scope_summary"
```

空库执行 `db-upgrade` 会一次性建立当前完整 schema。已升级到 `0013_query_log_scope_summary` 的数据库不会重复执行建表。

如果某个历史环境还停在旧增量链中间版本，不能直接用当前基线继续升级。应先使用旧迁移链升级到 `0013_query_log_scope_summary`，或重建数据库后执行当前基线迁移。

## 7. 启动 API

启动 API：

```bash
make PYTHON=.venv/bin/python api
```

默认等价于：

```bash
PYTHONPATH=apps/api LOG_LEVEL=INFO .venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

健康检查：

```bash
curl http://localhost:8000/health/live
curl http://localhost:8000/health/ready
```

`/health/live` 只表示进程存活。`/health/ready` 需要数据库、初始化状态、active config、ServiceBootstrap 和外部依赖都可用。

系统未初始化时，`/health/ready` 返回 `not_ready` 是正常现象；此时应先进入初始化流程。

## 8. 系统初始化

启动管理后台：

```bash
make admin
```

访问：

```text
http://localhost:5174/admin/setup-initialization
```

初始化流程会创建：

- 企业。
- 默认部门。
- 系统管理员账号。
- 内置角色。
- active config v1。
- Secret Store 中的 MinIO、JWT、模型 provider 等 secret。

初始化配置中的模型服务地址必须与实际环境一致。本地使用 compose 中的 TEI 服务时，通常配置：

| 类型 | 地址 |
| --- | --- |
| embedding | `http://localhost:8081` 或容器网络内对应地址 |
| rerank | `http://localhost:8082` 或容器网络内对应地址 |
| llm | 实际 OpenAI-compatible LLM provider 地址 |

如果 LLM provider 需要密钥，应在初始化页面填写对应 token。后端会写入 Secret Store，并在 active config 中保存 secret ref，而不是保存明文。

初始化完成后，再次检查：

```bash
curl http://localhost:8000/health/ready
```

正常情况下应看到：

```json
{
  "status": "ready",
  "checks": {
    "database_reachable": true,
    "migration_ready": true,
    "initialized": true,
    "active_config": true,
    "service_bootstrap": true
  }
}
```

## 9. 启动 Worker

文档导入必须启动 Worker。API 只负责创建导入任务，不负责执行解析、embedding 和索引发布。

启动单个 Worker：

```bash
make PYTHON=.venv/bin/python worker
```

启动多个 Worker：

```bash
make PYTHON=.venv/bin/python WORKER_ID=import-worker-1 worker
make PYTHON=.venv/bin/python WORKER_ID=import-worker-2 worker
```

或使用简写：

```bash
make PYTHON=.venv/bin/python worker-1
make PYTHON=.venv/bin/python worker-2
```

多个 Worker 适用于：

- 文档导入任务较多。
- embedding provider 吞吐足够。
- 需要验证任务锁接管和失败恢复。

不适合盲目增加 Worker 的场景：

- embedding / rerank / LLM provider 已经成为瓶颈。
- Qdrant 写入延迟较高。
- MinIO 或 PostgreSQL 连接数不足。

## 10. 启动前端

普通查询前端：

```bash
make web
```

访问：

```text
http://localhost:5173
```

管理后台：

```bash
make admin
```

访问：

```text
http://localhost:5174
```

前端 dev server 会代理 `/internal` 和 `/health` 到 API。若使用自定义 API 地址，检查 `.env`：

```bash
VITE_API_BASE_URL=http://localhost:8000
```

本地开发和生产部署的 API 地址处理方式不同：

- 本地开发可设置 `VITE_API_BASE_URL=http://localhost:8000`，让前端直接访问本地 API。
- 生产推荐将 `VITE_API_BASE_URL` 置空，前端使用同源相对路径，由网关代理 `/internal` 和 `/health` 到 API。
- 如果生产前端和 API 分属不同域名，前端构建时设置 `VITE_API_BASE_URL=https://api.example.com`，并由 API 网关配置 CORS。

`VITE_API_BASE_URL` 是构建期变量。生产前端 build 完成后，修改服务器 `.env` 不会改变已经生成的静态产物。

## 12. 管理后台使用流程

初始化完成并登录系统管理员后，建议按以下顺序准备可查询数据：

1. 在“部门管理”确认部门结构。
2. 在“用户管理”创建测试用户，并绑定对应部门和角色。
3. 在“知识库管理”创建知识库。
4. 设置知识库可见性和默认文档权限。
5. 在知识库文档管理中上传 Markdown、TXT、DOCX 或 PDF 文档。
6. 确认导入任务从 `queued` 推进到完成。
7. 在文档详情中查看文档版本、索引版本和 chunk 预览。
8. 在“查询诊断”查看查询日志、模型调用日志和检索诊断。

如果上传后任务一直停留在 `queued`，优先确认 Worker 是否启动。

## 13. 普通查询前端使用流程

普通用户登录后：

1. 系统会加载当前用户可访问的知识库。
2. 用户可以选择知识库，也可以由后端执行全权限知识库自动搜索。
3. 输入问题后，后端会执行 Query Rewrite、关键词召回、向量召回、融合、rerank、候选 gate、上下文构建、LLM 生成和 citation 校验。
4. 页面展示回答、降级状态、置信度和引用来源。
5. 多轮会话会保存到服务端，同一用户刷新或切换会话后可以恢复历史记录。

查询没有答案时，不应返回空白。后端会输出结构化降级说明，解释是未检索到相关内容、权限过滤后无可用片段、模型不可用，还是 citation 校验失败。

## 15. 备份

本地 PostgreSQL 备份：

```bash
make pg-backup
```

默认输出到：

```text
artifacts/backups/postgres-<timestamp>.dump
```

备份文件可能包含用户、配置、审计和业务元数据，不应提交到代码仓库。

生产或长期开发环境至少需要同时备份：

- PostgreSQL。
- MinIO bucket。
- Qdrant collection 数据或快照。
- `SECRET_STORE_MASTER_KEY`。
- `.env` 中必要的基础设施连接信息。

仅备份 PostgreSQL 而丢失 `SECRET_STORE_MASTER_KEY`，会导致 secrets 表中的密钥无法解密。

## 16. 常见故障

### 16.1 登录时报 `SERVICE_BOOTSTRAP_UNAVAILABLE`

含义：登录接口还没进入认证逻辑，就被 setup guard 拦截。

检查：

```bash
make PYTHON=.venv/bin/python db-current
curl http://localhost:8000/health/ready
```

常见原因：

- 数据库 migration 未到 head。
- 系统未初始化。
- active config 缺失或 schema 不合法。
- Redis、MinIO、Qdrant、embedding、rerank 或 LLM provider 不可用。
- Secret Store 中必要 secret 无法读取。

修复顺序：

```bash
make PYTHON=.venv/bin/python db-upgrade
curl http://localhost:8000/health/ready
```

根据 `bootstrap_checks` 中失败项继续处理。

### 16.2 文档导入一直是 `queued`

常见原因：Worker 没启动。

处理：

```bash
make PYTHON=.venv/bin/python worker
```

再到管理后台查看导入任务状态。

### 16.3 文档导入失败：`draft vector points cannot be written`

常见原因：

- Qdrant 不可用。
- collection 未创建或维度不匹配。
- embedding 维度和 active config 配置不一致。
- draft / active 索引发布状态异常。

检查：

```bash
curl http://localhost:6333/collections
curl http://localhost:8000/health/ready
```

管理后台可使用“索引运维”查看 collection health，并按需重建索引。

### 16.4 查询时报 `LLM_PROVIDER_HTTP_ERROR`

常见原因：

- LLM provider 地址错误。
- LLM provider token 缺失或失效。
- 初始化时没有正确写入 `llm_auth_token`。
- provider 非 OpenAI-compatible，接口协议不匹配。

检查：

- active config 中 LLM provider base URL。
- Secret Store 中 LLM token ref 是否可读。
- provider 访问日志中是否出现 401 / 403 / 5xx。
- 管理后台“模型调用日志”中的错误码和 caller。

### 16.5 查询无答案或降级

优先查看管理后台“查询诊断”：

- Query Rewrite 是否正确拆分。
- 关键词召回和向量召回数量。
- 权限 gate 拒绝原因。
- rerank 是否可用。
- 最终上下文片段是否覆盖用户问题。
- citation 校验是否通过。

常见原因：

- 用户没有可访问知识库。
- 文档未完成索引发布。
- 文档权限不允许当前用户读取。
- 候选相关性低，被 quality gate 拦截。
- LLM 生成了非法 citation，被系统拦截或自动修复。

### 16.6 `/health/ready` 中 Redis 通过，但缓存没有效果

当前 Redis 只作为基础设施和 ServiceBootstrap 依赖检查项，业务缓存能力尚未接入。配置缓存目前是进程内短 TTL 缓存，查询缓存表目前是结构预留，不等同于 Redis 查询缓存。

## 17. 开发和发布注意事项

- 不要把真实密钥、token、密码、完整 prompt 或业务文档原文提交到仓库。
- `.env` 不应提交。
- `artifacts/` 下的测试记录和备份默认不提交。
- 高风险写操作前应确认目标环境，尤其是 `make reset`。
- API、Worker 和前端修改后，应运行对应测试或构建命令。
- 数据库结构变更后必须同步迁移、契约文档、后端实现和测试。
- 当前迁移是 schema 基线，新增结构变更应从当前 head 继续追加新的 migration，不要修改已发布基线语义来修历史环境。

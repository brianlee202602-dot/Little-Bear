# 备份与恢复说明

更新时间：2026-06-03

本文说明 Little Bear 当前实现下的数据备份、恢复顺序和风险边界。PostgreSQL 是业务事实源；MinIO、Qdrant、Redis 属于外部状态或派生状态，恢复时必须按业务事实源重新校验。

## 数据分层

### 必须备份

- PostgreSQL：企业、用户、部门、权限、知识库、文档、chunk 元数据、索引版本、导入任务、配置、审计、查询日志、模型调用日志。
- MinIO：原始文件、解析结果、清洗结果、完整 chunk 正文对象。
- Secret Store master key：用于解密数据库中的 secret value。

### 应备份

- Qdrant：active collection、向量点、权限 payload、快照。
- 配置版本和 active config 指针已经在 PostgreSQL 中，但恢复后仍需重新执行 ServiceBootstrap 校验。

### 通常不作为业务事实源备份

- Redis：缓存、锁、通知和限流等派生运行状态。当前业务缓存能力尚未完整启用，Redis 恢复失败不应改变 PostgreSQL 事实状态。

## PostgreSQL 备份

当前 Makefile 提供 PostgreSQL 备份命令：

```bash
make pg-backup
```

默认输出：

```text
artifacts/backups/postgres-<timestamp>.dump
```

该命令使用 `pg_dump -Fc` 生成 custom format dump。备份文件可能包含用户、权限、配置引用、日志和业务元数据，不应提交到 Git。

## MinIO 备份

MinIO 中保存：

- 上传原始文件。
- 解析和清洗后的文件。
- chunk 完整正文对象。

当前仓库未提供独立 MinIO 备份 Makefile 目标。开发或内部环境可按 MinIO 官方客户端 `mc mirror` 或对象存储平台自身快照能力执行。备份时应至少覆盖当前 active config 指向的 bucket。

恢复 PostgreSQL 后如果 MinIO 对象缺失，会影响：

- 文档来源预览。
- chunk 完整正文回源读取。
- 查询上下文补全。
- 重建索引时的源内容读取。

## Qdrant 快照

管理后台“索引运维”提供 Qdrant collection 级操作入口，对应后端能力包括：

- 查询 collection health。
- 列出 collection snapshots。
- 创建 collection snapshot。
- 从 snapshot recovery。
- 对 collection 创建重建索引任务。

相关接口位于：

```text
/internal/v1/admin/index-health
/internal/v1/admin/index-collections/{collection_name}/snapshots
/internal/v1/admin/index-collections/{collection_name}/snapshot-recoveries
/internal/v1/admin/index-collections/{collection_name}/rebuild-jobs
```

这些操作需要 `document:index` 权限，并要求高风险确认 header。管理后台会在交互层提示确认，后端仍会再次校验。

## 推荐备份顺序

为了减少导入和索引过程中的不一致，建议：

1. 暂停 Worker 或停止提交新的导入 / 重建索引任务。
2. 确认 API 仍可读，数据库迁移版本正确。
3. 执行 PostgreSQL 备份。
4. 执行 MinIO 对象备份。
5. 创建 Qdrant collection snapshot。
6. 保存备份清单：时间、迁移版本、active config version、Qdrant collection 名称、MinIO bucket、Secret Store master key 版本。
7. 恢复 Worker。

如果不能暂停 Worker，备份仍可进行，但恢复后必须执行索引健康检查，并对异常 collection 或文档执行重建索引。

## 推荐恢复顺序

1. 停止 API 和 Worker。
2. 恢复 PostgreSQL。
3. 恢复 Secret Store master key。
4. 恢复 MinIO bucket 和对象。
5. 恢复 Qdrant collection snapshot，或跳过 Qdrant 恢复并后续全量重建索引。
6. 启动基础设施。
7. 执行数据库迁移到 head：

```bash
make PYTHON=.venv/bin/python db-upgrade
```

8. 启动 API。
9. 检查 `/health/ready` 和 ServiceBootstrap。
10. 在管理后台“索引运维”刷新索引健康。
11. 对异常 collection 或文档创建重建索引任务。
12. 启动 Worker，等待任务完成。
13. 执行 smoke 和查询回归：

```bash
make PYTHON=.venv/bin/python smoke-p0
make PYTHON=.venv/bin/python query-regression-rag
```

## PostgreSQL 手工恢复示例

当前 Makefile 未提供 `pg-restore` 目标。可按环境手工执行：

```bash
docker compose --env-file .env exec -T postgres sh -lc 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
docker compose --env-file .env exec -T postgres sh -lc 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < artifacts/backups/postgres-xxx.dump
```

执行前必须确认这是要恢复的环境。不要在未确认环境和备份文件的情况下清空数据库。

## 恢复后的校验清单

- `make PYTHON=.venv/bin/python db-current` 显示迁移版本正确。
- API ready。
- active config 存在且可 bootstrap。
- 管理员可以登录管理后台。
- 管理后台配置、用户、部门、知识库列表可读。
- 文档来源预览可读。
- 索引健康无异常，或异常已创建重建任务。
- 查询能返回有权限的引用。
- deleted / blocked / draft / archived 内容不可被查询命中。
- query log 和 model call log 正常写入。

## 风险边界

- 只有 PostgreSQL 备份但没有 MinIO 备份时，文档元数据可恢复，但源文件和 chunk 正文可能不可读。
- 只有 PostgreSQL 备份但没有 Qdrant 备份时，可通过重建索引恢复查询能力。
- Secret Store master key 丢失时，数据库中的 secret value 无法解密，需要重新写入相关密钥并重新发布配置。
- Redis 数据丢失不应破坏业务事实，但可能影响短期缓存、锁和限流状态。
- 恢复后不要直接信任 Qdrant 中的旧 payload，必须通过索引健康、权限过滤和 citation 校验闭环确认。

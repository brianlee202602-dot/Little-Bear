# 生产部署拓扑说明

更新时间：2026-06-03

本文说明 Little Bear 按当前代码实现可以形成的生产部署拓扑。本文不描述尚未落地的 Kubernetes / Helm 编排，也不假设仓库中已经存在镜像流水线。

## 1. 部署目标

当前系统的生产拓扑应满足：

- API 与 Worker 分离部署。
- PostgreSQL 作为业务事实源外部化部署。
- MinIO、Qdrant、Redis 和模型 provider 外部化部署。
- API 可以多副本水平扩展。
- Worker 可以多副本并发消费导入任务。
- 前端静态资源由独立 Web 服务或网关提供。
- 所有业务配置通过 active config 和 Secret Store 管理。

## 2. 组件拓扑

```text
用户浏览器
  -> Web 网关 / 静态资源服务
      -> apps/web 普通查询前端
      -> apps/admin 管理后台前端
  -> API 网关 / 反向代理
      -> API 副本 1..N
          -> PostgreSQL
          -> Redis
          -> MinIO
          -> Qdrant
          -> embedding / rerank / LLM provider
      -> Worker 副本 1..N
          -> PostgreSQL
          -> MinIO
          -> Qdrant
          -> embedding provider
```

API 和 Worker 都依赖 PostgreSQL 中的 active config，不应在不同副本中手工配置不同业务参数。

## 3. API 多副本

API 当前是 FastAPI 应用，启动入口为：

```bash
make PYTHON=.venv/bin/python api
```

生产环境应使用进程管理器或容器运行等价入口：

```bash
PYTHONPATH=apps/api python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

API 多副本部署要点：

- API 不在本地磁盘保存业务事实。
- PostgreSQL 是事实源。
- MinIO 保存文件对象。
- Qdrant 保存向量索引。
- active config 有进程内短 TTL 缓存，配置发布后各副本会在缓存失效后读取新配置。
- API health ready 必须通过后再接入流量。

健康检查：

- `/health/live`：进程存活。
- `/health/ready`：数据库、初始化状态、active config、ServiceBootstrap 和关键依赖可用。

`APP_ENV=production` 时，FastAPI docs 和 redoc 会关闭。

## 4. Worker 多副本

Worker 启动入口为：

```bash
make PYTHON=.venv/bin/python worker
```

也可以指定 worker id：

```bash
make PYTHON=.venv/bin/python worker-1
make PYTHON=.venv/bin/python worker-2
```

Worker 多副本并发依赖 PostgreSQL 中的 import job 锁：

- 每个 Worker 领取任务时写入 `locked_by` 和 `locked_until`。
- Worker 周期性 heartbeat 延长锁。
- Worker 崩溃后，锁过期，其他 Worker 可以接管。
- `WORKER_ID` 为空时会自动使用 `worker-<pid>`。

生产建议：

- 每个 Worker 副本使用稳定且可识别的 `WORKER_ID`。
- 根据 embedding provider、MinIO、Qdrant 和 PostgreSQL 压力控制 Worker 副本数。
- Worker 与 API 使用同一个 active config。
- Worker 不通过 FastAPI route 执行业务逻辑，直接调用导入运行时和 service。

## 5. PostgreSQL

PostgreSQL 是当前系统事实源，承载：

- 组织、用户、角色和权限。
- active config 和 Secret Store 密文。
- 知识库、文档、chunk、索引账本。
- import job。
- query log、model call log、audit log。
- query conversation。
- query cache 预留账本。

部署要求：

- 使用支持当前扩展的 PostgreSQL 环境。
- 迁移必须先执行到当前 head。
- 不允许多个环境共用同一个生产数据库。
- 备份优先覆盖 PostgreSQL。

当前 Makefile 提供 PostgreSQL 备份入口：

```bash
make pg-backup
```

## 6. MinIO

MinIO 保存：

- 原始上传文件。
- 解析结果。
- 清洗结果。
- 完整 chunk 文本对象。

部署要求：

- bucket 名称由 active config 管理。
- access key 和 secret key 由 Secret Store 保存。
- API 和 Worker 必须能访问同一 MinIO bucket。
- 生产环境应启用访问控制、持久化和独立备份。

MinIO 不替代 PostgreSQL 中的文档、版本和索引事实。

## 7. Qdrant

Qdrant 保存 chunk 向量索引。

部署要求：

- collection 名称和连接地址由 active config 管理。
- API key 如启用，应写入 Secret Store。
- collection 维度必须与 embedding 模型维度一致。
- draft vector 发布前不得对查询可见。
- index health 页面用于对比 PostgreSQL 索引账本和 Qdrant 状态。

当前管理后台已提供 Qdrant 快照和索引运维入口，但 Qdrant 集群级备份、跨节点复制和恢复流程需要按部署环境单独配置。

## 8. Redis

Redis 当前部署角色：

- ServiceBootstrap 外部依赖检查。
- 未来缓存、锁、限流、配置通知的基础设施。

当前 Redis 尚未承载业务缓存读写。Redis 不可用时，当前代码不会自动进入“无缓存运行”；ready 会失败。

生产环境仍应部署 Redis，因为 active config 和 ServiceBootstrap 当前要求 Redis 可达。

## 9. 模型 provider

当前系统依赖 OpenAI-compatible 或等价 HTTP provider：

- embedding provider。
- rerank provider。
- LLM provider。

本地 compose 中的 TEI embedding / rerank 只用于演示和联调。生产环境可以替换为外部 provider，但必须在 active config 中配置 provider base_url、healthcheck 和认证 token ref。

模型 provider 部署要求：

- provider 健康检查可访问。
- 认证 token 写入 Secret Store。
- embedding 维度与 Qdrant collection 一致。
- LLM provider 超时、HTTP 错误和 citation 异常会进入降级或 fail closed 逻辑。

## 10. 前端部署

普通查询前端：

```bash
npm run build:web
```

管理后台：

```bash
npm run build:admin
```

开发环境中 Vite 默认：

- `apps/web` 端口 `5173`。
- `apps/admin` 端口 `5174`。
- `/internal` 和 `/health` 代理到 `http://127.0.0.1:8000`。

生产环境应由 Web 网关或静态资源服务托管构建产物，并将 `/internal` 与 `/health` 转发到 API 网关。

## 11. 网络与端口

默认端口：

| 组件 | 默认端口 |
| --- | --- |
| API | `8000` |
| 普通查询前端 dev server | `5173` |
| 管理后台 dev server | `5174` |
| PostgreSQL | `5432` |
| Redis | `6379` |
| MinIO API | `9000` |
| MinIO Console | `9001` |
| Qdrant HTTP | `6333` |
| Qdrant gRPC | `6334` |
| TEI embedding | `8081` |
| TEI rerank | `8082` |

生产环境不应直接暴露 PostgreSQL、Redis、MinIO 内部 API、Qdrant 和模型 provider 给普通用户网络。

## 12. 安全边界

部署时必须保持：

- 外部用户只访问前端和 API 网关。
- 管理后台应有访问控制和账号权限限制。
- Secret value 不提交代码库，不写入前端。
- active config 中只保存 secret ref。
- `SECRET_STORE_MASTER_KEY` 必须稳定保存，不能丢失。
- JWT signing key 应由 Secret Store 提供。
- API 与 Worker 使用同一数据库和 active config。
- TLS 终止由网关或反向代理处理，当前 FastAPI 进程不内置 TLS 配置。

## 13. 日志、备份、恢复和告警

当前代码提供：

- API / Worker 进程日志。
- query log。
- model call log。
- audit log。
- index health。
- PostgreSQL 备份 Makefile 入口。
- Qdrant 快照管理入口。

当前代码未内置：

- OpenTelemetry。
- Prometheus 指标接口。
- 自动告警规则。
- Kubernetes readiness / liveness manifest。
- MinIO 自动备份编排。

生产部署时应在外部平台补齐日志采集、告警、备份和恢复演练。

## 14. 当前边界

- 当前仓库没有生产镜像构建流水线。
- 当前仓库没有 Kubernetes / Helm 编排。
- 当前 Redis 无业务缓存读写。
- 当前日志是进程日志和数据库日志事实源，不是完整分布式追踪。
- 当前生产拓扑说明是按现有代码运行形态给出的部署边界，不代表已有云平台脚本。

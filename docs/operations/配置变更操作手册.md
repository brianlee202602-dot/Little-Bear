# 配置变更操作手册

更新时间：2026-06-03

本文说明 Little Bear 当前配置管理的操作流程、权限要求、确认机制和失败处理。配置是业务运行时事实的一部分，不应通过 `.env` 临时绕过。

## 配置模型

当前配置由 PostgreSQL 中的配置版本承载，并通过 active config 驱动业务运行时。

配置覆盖：

- Redis、MinIO、Qdrant 等外部依赖。
- embedding、rerank、LLM provider。
- 模型名称、维度、normalize、temperature、max_tokens。
- 检索策略、rerank 参数、context token 预算。
- 权限策略、缓存策略、限流策略、降级策略、审计策略。
- 超时预算。

启动层只允许读取数据库连接和进程级参数。业务模块必须通过 `ConfigService` 加载 active config。

## 权限要求

配置管理需要系统管理员或具备配置管理能力的账号。

常见能力：

- `config:read`：读取配置列表、详情、配置项。
- `config:manage`：创建、编辑、校验、发布、归档配置。

前端只负责隐藏不可操作按钮；后端会在每个接口重新校验权限。

## 操作入口

管理后台：

```text
配置管理
```

后端主要接口：

```text
GET    /internal/v1/config-versions
POST   /internal/v1/config-versions
GET    /internal/v1/config-versions/{version_id}
PUT    /internal/v1/config-versions/{version_id}
PATCH  /internal/v1/config-versions/{version_id}/active
PATCH  /internal/v1/config-versions/{version_id}/archive
DELETE /internal/v1/config-versions/{version_id}
POST   /internal/v1/config-validations
GET    /internal/v1/config-items
PUT    /internal/v1/config-items/{key}
```

接口字段细节以 FastAPI OpenAPI 和 `docs/contracts/openapi.yaml` 为准。

## 新建配置版本

适用场景：

- 接入新的模型 provider。
- 调整检索或 rerank 策略。
- 切换外部依赖地址。
- 大范围调整权限、降级、审计或限流策略。

操作流程：

1. 进入“配置管理”。
2. 点击“新建版本”。
3. 按可视化表单填写配置。
4. 执行配置校验。
5. 保存为 draft。
6. 确认无误后激活。

后端创建 draft 时需要确认 header：

```text
x-config-confirm: save-draft
```

管理后台会在操作确认后携带该 header。

## 编辑配置版本

编辑保存是更新当前选择版本，不自动产生新版本。

适用场景：

- 修正 draft 配置。
- 修改尚未归档的 inactive 配置。
- 对当前版本做可控更新。

操作流程：

1. 在配置列表选择版本。
2. 点击“编辑”。
3. 在可视化表单中修改配置项。
4. 执行校验。
5. 保存。
6. 如需生效，再执行激活。

高风险配置项保存仍需要确认 header：

```text
x-config-confirm: save-draft
```

## 激活配置

激活配置会改变系统 active config。后端执行：

1. 锁定目标配置版本。
2. 标记为 validating。
3. 执行 JSON Schema 校验。
4. 执行依赖校验和 ServiceBootstrap。
5. 校验通过后停用旧 active version。
6. 将目标版本标记为 active。
7. 更新 active_config_version 指针。
8. 持久化 bootstrap 结果。
9. 失效配置缓存。
10. 写入配置发布审计。

激活需要确认 header：

```text
x-config-confirm: publish
```

如果依赖校验失败：

- 目标版本会被标记为 failed。
- active pointer 不会切换。
- 后端返回 `CONFIG_DEPENDENCY_FAILED`。
- 审计记录 `config.publish_failed`。

## 归档配置

归档用于避免管理员误激活已经不可用或过期的配置。

归档需要确认 header：

```text
x-config-confirm: archive
```

归档后不应再作为可激活候选。删除操作在交付版中等价于归档语义，不代表物理删除配置事实。

## 回滚配置

当前设计支持在多个配置版本中切换。回滚不是“恢复文件”，而是重新激活一个仍可用的历史版本。

回滚流程：

1. 在配置列表找到目标历史版本。
2. 查看详情，确认 provider、secret refs、模型名称、检索策略仍可用。
3. 执行配置校验。
4. 激活该版本。
5. 检查 ServiceBootstrap。
6. 执行 smoke 和查询回归。

如果历史版本引用的 secret 已被删除或 provider 地址不可达，回滚会失败。

## Secret 配置规则

配置中不应保存明文密钥，应保存 secret ref，例如：

```text
secret://rag/model/llm-api-key
secret://rag/model/embedding-api-key
secret://rag/model/rerank-api-key
secret://rag/qdrant/api-key
```

Secret value 由 Secret Store 加密保存。普通日志、配置列表、模型调用日志和审计不得展示 secret value。

## Provider 配置变更检查

修改模型 provider 后至少检查：

- provider `base_url`。
- provider `type`。
- embeddings / rerank / chat path 是否匹配 provider 协议。
- auth secret ref 是否存在。
- embedding dimension 是否与 Qdrant collection 一致。
- timeout 是否合理。
- rerank unavailable 时是否允许降级。
- LLM 401 / 403 是否由密钥配置错误导致。

## 变更后验证

最低验证：

```bash
make PYTHON=.venv/bin/python smoke-p0
make PYTHON=.venv/bin/python query-regression-rag
```

涉及前端配置管理页面：

```bash
npm run typecheck:admin
npm run build:admin
```

涉及 provider 接入或检索策略：

```bash
make PYTHON=.venv/bin/python test-integration-qdrant
```

## 禁止事项

- 禁止通过 `.env` 注入业务配置绕过 active config。
- 禁止在配置列表返回完整 secret、完整 prompt 或内部 hash。
- 禁止激活未通过 schema 和依赖校验的配置。
- 禁止为了让配置发布成功而关闭 ServiceBootstrap。
- 禁止把配置审计当作可选项。
